# 바위 협곡 10k 성능 진단

## 최적화 적용 결과

정적 장애물 BVH를 추가하고 경로 검사·접촉 후 정적 보정·연속 이동·벽 겹침 통계에
후보 조회를 적용했다. 작은 조회는 64px 타일과 32px 여유 영역의 후보를 캐시한다.
지형 좌표가 바뀌면 트리와 캐시를 갱신하며, 8개 이하의 장애물은 기존 순차 검사를 쓴다.
작은 영역의 후보 캐시는 추가 장애물을 포함할 수 있지만 최종 판정은 기존 정확한
거리·충돌 함수를 사용한다. 기존 장애물 순서도 유지한다.

| 바위 협곡 10k | 적용 전 | 적용 후 |
|---|---:|---:|
| 스텝 평균 | 92.56ms | 31.01ms |
| 스텝 P95 | 102.20ms | 37.20ms |
| 경로 샘플링 평균 | 53.04ms | 7.27ms |
| 접촉·이동 평균 | 27.56ms | 16.10ms |
| 앱 실행 루프 평균 | 9.15fps | 27.19fps |

동일 프로토콜의 별도 headless Chromium 실측으로 스텝 처리 시간이 약 66.5% 감소했다.
바위 협곡 1k도 9.58→2.71ms, 평지 10k는 13.72→13.52ms였다.
각 비교 조건의 150스텝 상태 해시는 모두 적용 전과 일치하며 벽 겹침은 0건이다.
원시 결과: [적용 전](measurements/rocky-pass-before.json),
[적용 후](measurements/rocky-pass-after.json).

검증: 빌드 및 타입 검사 통과. 충돌·경로·혼합 크기·회전·코너 회복 등 관련 테스트
62개 통과 후, 후보 캐시 추가에 해당하는 경로·인덱스·동등성 테스트 16개를 재실행해 통과했다.
브라우저의 10k 배치, 바위 협곡 600스텝, 동적 지형 변경 검증 3개도 통과했다.
추가한 동등성 검사는 4가지 조건에서 480스텝을 실행하며 목표 변경·장애물 설치/철거를
포함하고, 전체 장애물 순회와 30스텝마다 상태 해시 및 이동 지표를 비교한다.

접촉 반복 수·안전 판정·객체 크기·속도·지형은 최적화로 변경하지 않았다.
아직 60fps를 달성한 것은 아니다. 다음 큰 비용은 객체 간 접촉 계산과 긴 시야 선분의
후보 조회다. 전체 테스트 모음·전체 브라우저 모음·장시간 10k 도착 검증은 실행하지 않았다.
아래는 최적화 이전 진단 기록이다.

## 측정 조건

현재 작업 디렉터리의 Vite 개발 서버와 Playwright의 별도 headless Chromium을 사용했다.
사용자가 열어 둔 브라우저와 시뮬레이션은 변경하지 않았다. seed=42, 기본 반경 3.2,
품질 감사 OFF, 동일 밀도 확장 ON. 비교 시나리오마다 새 페이지에서 30스텝 예열 후
120스텝을 측정했다. 모든 경우 측정 종료 시 전체 객체가 활성 상태였고 벽 겹침은 0건이었다.
현재 작업 중인 이동 솔버 변경을 포함한 작업 디렉터리 기준이며, 커밋 버전의 결과가 아니다.

| 조건 | 장애물 | 월드 | 스텝 평균 / P95 | 렌더 CPU 평균 |
|---|---:|---|---:|---:|
| 바위 협곡 1k | 158 | 1200×720 | 9.58 / 10.50ms | 0.22ms |
| 평지 10k | 0 | 약 3795×2277 | 13.72 / 15.60ms | 0.95ms |
| 바위 협곡 10k | 158 | 약 3795×2277 | 92.56 / 102.20ms | 1.10ms |

렌더 CPU는 별도 CanvasRenderer의 10회 예열 후 60회 호출 시간이다. GPU 합성·화면 표시
시간을 포함하지 않는다. 추가로 바위 협곡 10k의 실제 앱 실행 루프에서 초기 10프레임을
제외한 80프레임을 관찰했으며 평균 9.15fps, render 호출 평균 1.02ms였다.
headless 측정이므로 사용자의 표시 창 FPS와 동일하다는 의미는 아니다.

## 병목과 우선순위

1. **경로 샘플링의 장애물 검사 — 53.04ms/step, 약 57%.**
   `FlowField.sampleDirection()`은 목적지 직선 시야와 짧은 전방 구간을 검사한다.
   `isSegmentSafe()`는 장애물 전체에 `segmentDistanceSquaredToRect()`를 실행한다.
   이 함수는 선분 교차뿐 아니라 끝점과 네 모서리의 거리도 계산한다.
   CPU 샘플에서도 이 거리 함수와 `segmentIntersectsRect()`가 가장 큰 비용으로 확인됐다.
   우선 선분의 clearance 확장 AABB와 겹치지 않는 장애물을 간단한 비교로 제외하고,
   이후 정적 장애물 공간 인덱스와 선분을 따라 방문하는 셀 조회를 적용할 가치가 크다.
   후보에 대해서는 기존 정확한 거리 검사와 수치 허용 오차를 유지해야 한다.
   UI의 `navigation` 시간은 방향장 재계산 시간이고, 이 병목은 `desired`에 기록된다.
   고정 방향장을 공유하더라도 매 객체의 이 검사는 계속 실행된다.

2. **접촉·정적 이동 — 27.56ms/step, 약 30%.**
   `CrowdMovementSolver.projectOutsideStatics()`는 접촉 보정 뒤 모든 장애물을 순회한다.
   접촉 반복은 8회이며, 매 반복에서 보정된 객체가 검사 대상이다.
   `canIntegrateDirectly()`와 정밀 sweep에도 전체 장애물 순회가 있다.
   프로파일에서는 `projectPredictionsOutsideStatics()`가 두 번째로 큰 자체 시간을 보였다.
   정적 공간 인덱스를 공유하여 객체 주변이나 이동 구간의 후보만 검사하는 것이 우선이다.
   보정으로 위치가 바뀌는 경우 후보 갱신이 필요하며, 충돌 처리 순서를 유지해야 한다.
   접촉 반복 수나 안전 검사를 단순히 줄이는 방식은 이번 권고에 포함하지 않는다.

3. **매 스텝 통계의 벽 검사.** `CrowdSimulation.finalizeMetrics()`도 객체마다 장애물
   전체를 순회한다. 10k×158이면 이 루프만 최대 158만 번/step이다.
   위 공간 인덱스를 여기에도 적용하면 진단을 유지하면서 비용을 줄일 수 있다.
   주요 pass 합계 밖의 비용은 평균 약 6.0ms이며, 모두 이 함수의 비용이라는 뜻은 아니다.

4. **유체 격자와 렌더링은 후순위.** 유체 속도·압력 처리 5.24ms, 밀도 처리 0.72ms.
   확장 시 격자가 50×30에서 159×95로 늘어나므로 격자 비용도 커진다.
   점유된 타일 위주 처리 등은 압력 전파의 경계를 보존해야 하는 후속 최적화다.
   렌더러는 확장 월드에서 픽셀 레이어 경로를 끄고 10k개의 `fillRect`를 호출한다.
   화면 좌표 기반 일괄 렌더링을 고려할 수 있지만, 현재 약 1ms라 주 병목 해결보다 효과가 작다.

60fps의 프레임 예산은 약 16.7ms다. 현재 92.6ms의 시뮬레이션 비용이 이를 크게 초과한다.
기본 1× 속도에서는 FixedClock이 프레임당 최대 한 스텝만 수행하므로,
여러 스텝을 무한히 따라잡으려는 루프가 현재 저하의 원인은 아니다.
Worker로 이동하면 UI 응답성은 개선할 수 있지만 계산량 자체를 줄이지는 않는다.

## 재현 및 한계

```powershell
npm run dev
node scripts/profile-performance.mjs http://127.0.0.1:4273
```

원시 측정은 `test-results/performance-profile/summary.json`, 60스텝 CPU 샘플은
`test-results/performance-profile/rocky-10k.cpuprofile`에 저장된다.
CPU 프로파일의 위치는 Vite가 변환한 JavaScript 기준이므로 원본 TS 줄 번호와 다르다.
스크립트는 별도 브라우저 안에서 측정용 렌더 래퍼를 설치하고 종료 시 브라우저를 닫는다.

최초 진단에서는 런타임 최적화를 적용하지 않았으며, 이후 적용 결과는 문서 상단에 기록했다.
장시간 이동·후반 병목과 GPU 실측은 범위 밖이다.
