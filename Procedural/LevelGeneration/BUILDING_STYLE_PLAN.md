# 데이터 기반 건축 스타일 — building-patterns-v1

구현: 2026-09-17. 대상은 `Procedural/LevelGeneration`이며 기존 직접 편집과 v1~v3 생성 계약을 유지한다. 상가형과 업무형은 이 프로젝트에서 만든 예시이며 City Sample 스타일의 복제품이 아니다.

## 공식 발표에서 가져온 개념

사용자가 확인해 제공한 [The Matrix Awakens: Generating a World 공식 발표](https://www.youtube.com/watch?v=usJrcwN6T4I)의 타임코드를 근거로 삼았다. 이번 작업에서 웹 도구로 영상 본문을 직접 추출하지는 못했다. 발표자인 [Quentin Marmier의 제작 설명](https://quentinmarmier.artstation.com/projects/xYeKNO)에서도 해당 공식 발표 링크를 확인했다.

| 구간 | 제공된 조사에서 확인한 개념 | 이번 프로젝트의 적용 |
| --- | --- | --- |
| 26:39~26:51 | JSON BDF, 층별 모듈 정의, Facade Shape Grammar, Level Grammar | 타입이 있는 `BuildingStyle` 데이터 |
| 27:18~27:33 | levels에서 층 간격을 구해 부피 분할 | 정수 Grid의 Y 행에 ground/middle/top 역할 부여 |
| 27:36~27:55 | Corner Cap이 Split Corner보다 우선 | 모서리 자리를 먼저 확보한 뒤 가로 패턴 배치 |
| 27:59~28:39 | 모듈 키, 구간, 반복/고정 묶음, 스케일 가능 표시 | `start/repeat/end`, 최소·최대 반복 수, 완전한 연결 묶음 |

원본 BDF 문자열 문법, 스케일 문법, Houdini 처리 및 개별 스타일을 구현하거나 복제한 것은 아니다. 아래의 지면, 정면, 정렬, 잔여 폭 정책은 이 프로젝트에서 추가한 설계다.

## 구현 순서와 책임

`Grid → 기존 외피/Region 분석 → 기본 타일 선택 → 층·Facade 패턴 → 지붕/처마·상단 장식 → coverage 검증 → 공유 에셋 인스턴싱`

- `core/building-style.ts`: 스타일/층/모듈/패턴 타입, 상가형·업무형 데이터, 정의 검증과 층 역할 해석.
- `core/facade-patterns.ts`: 실제 연속 구간 추출, 정면/출입구, 모서리 확보, 정수 폭 평가, 반복층 정렬과 선택 Trace.
- `core/facade-assets.ts`: 스타일과 독립된 에셋 ID/고정 치수, 접합 방향과 장식 bounds.
- `crafted-geometry.ts`, `panel-assets.ts`: 정해진 에셋의 geometry/material. 스타일 ID나 건물 높이로 에셋을 재선택하지 않는다.
- `viewer.ts`: 기존 배치 변환과 instancing으로 벽·프레임·유리를 표시. 한 칸마다 최종 geometry를 만들지 않는다.
- `core/document.ts`: v4 문서에 실제 스타일 정의를 보존. `documentOptions()`가 저장된 정의를 생성에 전달한다.

## 스타일 정의와 지원 문법

`BuildingStyle`에는 ID/양의 정수 버전, 모듈 목록, 패턴 목록, 층 정의, 단층 역할, 기본 벽, 출입구, 모서리 모듈/최소 폭, 상단 마감과 정면 방향 순서가 있다.

`LevelDefinition`은 역할, 고정 행 수 또는 `remaining`, 허용 모듈 세트, 후보 패턴 ID 목록과 선택적인 `align` 키를 가진다. ground → middle → top 순서를 지원하며 middle만 남는 높이를 반복한다. 기본값은 1 / remaining / 1이다. 짧은 건물은 최소 한 행의 top을 확보하고 ground의 고정 횟수를 줄인다. 단층은 `singleStorey`로 지정한 역할과 로컬 상단 마감을 함께 가진다.

`BuildingModule`은 의미, 에셋 ID, 정수 폭/높이, 허용 벽 방향과 연결 family/part를 가진다. 이번 버전의 구조 모듈은 **모두 1×1**만 지원한다. 선언만 큰 폭/높이로 바꾼 모듈은 거부한다. 연결 디자인은 여러 개의 단위 모듈 목록으로 정의한다.

`FacadePattern`은 고정 `start/end`, 반복 `repeat`, `minRepeat/maxRepeat`(1~32), 적용 층·정면/측면, 최소 폭, 우선순위와 잔여 폭을 채울 `remainder` 단독 모듈을 가진다. 각 시작/반복/끝 목록은 스스로 완결된 연결 묶음이어야 한다. 문자열 DSL, 중첩 재귀 문법, 임의 스크립트, 모듈 stretching은 없다.

정의 변경은 실제 결과에 반영된다. 예를 들어 업무형의 `office-pairs.repeat`를 `['office-single', 'office-pier']`로 바꾸면 반복층이 단독 창문과 기둥으로 구성된다. 수정 후 정의의 버전을 올리고 다음 경로로 저장/재생성할 수 있다.

```ts
const definition = structuredClone(OFFICE_STYLE);
definition.version = 2;
definition.patterns.find(p => p.id === "office-pairs")!.repeat =
  ["office-single", "office-pier"];
const doc = createDocument(grid, seed, "office", definition);
const result = generate(doc.grid, documentOptions(doc));
const saved = exportDocument(doc);
```

앱에서 저장한 JSON의 `buildingDefinition`을 편집하고 불러오는 경로도 같다. 그리드 편집·Seed 변경·새 부피·Fixture 변경과 Undo/Redo는 현재 정의를 보존한다. 다른 스타일을 선택하면 선택한 예시의 정의로 전환한다.

## 층과 지면 정책

- 연결 성분의 minY/maxY로 건물 전체의 층 역할을 계산한다. 기본 1층은 ground, 2층은 ground/top, 3층 이상은 ground/middle…/top이다.
- 실제 지형 정보가 없으므로 **성분 최하단 Y=0, 해당 셀 Y=0, 아래 셀 비어 있음**을 지면 접촉 기준으로 고정한다. 표시용 지면 슬라이더는 무관하다. 떠 있는 성분과 Y=0 아래로 이어진 성분에는 출입구를 만들지 않는다.
- 같은 벽 방향의 바로 위 면이 없으면 로컬 상단 경계로 판정한다. 성분 최고 높이와 일치하지 않아도 상단 장식을 부착한다. 낮은 별동, 단차/테라스와 통로 위 경계를 포함한다.
- 건물 전체에서 middle인 면도 로컬 상단 마감을 가질 수 있다. 전역 층 역할과 국소 경계는 Inspector에서 따로 표시한다.

## 정면, 연속 구간과 후보 선택

외피의 동일 Region·방향·Y·상단 경계 상태를 로컬 가로축 `u`로 정렬하고, 실제 인접한 열만 연속 구간으로 묶는다. 구멍을 바운딩 박스로 메우지 않는다.

접지 가능한 실제 연속 줄 중 가장 긴 줄을 정면으로 고른다. 동률은 스타일의 방향 순서(기본 PZ/PX/NZ/NX), ASCII Face ID 순서다. 가운데 셀 한 곳을 출입구로 정하며, 같은 성분/방향/평면의 다른 층도 정면으로 취급한다. 이 정책은 실제 도로나 건물의 용도를 추정하지 않는다.

현재 스타일 v2는 폭 3 이상 구간에서 (보존된 v1은 폭 4 이상) 수직 볼록 모서리의 칸을 먼저 모서리/기둥으로 확보한다. 출입구가 겹치면 출입구가 우선이다. 폭 1~2에서는 단순 구성을 허용한다. 모서리·문이 확보되면 그 사이의 연속 구간을 다시 분할한다.

후보는 다음 순서로 고른다.

1. 층, 정면/측면, 최소 폭, 모듈 세트, 방향, 연결 완결성, 공유 배열 조건을 만족해야 한다.
2. 정확히 채우는 후보를 우선한다.
3. 정렬 앞쪽 보충과 뒤쪽 잔여 칸의 합을 최소화한다.
4. 스타일 우선순위가 높은 후보를 고른다.
5. 동률은 패턴 ID의 ASCII 오름차순이다. 독립적인 층별 추첨은 하지 않는다.

각 후보의 가능한 최대 반복 횟수를 정수로 계산한다. 이것이 그 후보의 보충 칸 수를 최소화한다. 맞는 묶음이 없으면 해당 층/벽면 후보의 허용 단독 모듈로 내려가며, 그것도 없으면 기본 벽으로 채운다. 누락/반쪽 연결 패턴을 남기지 않는다.

`align`을 공유하는 층은 같은 Region과 정면/측면 안에서 가장 넓은 실제 구간부터 하나의 패턴 ID와 기준 열을 결정한다. 그 뒤 다른 층은 같은 반복 주기를 사용한다. 좁아지거나 구멍으로 나뉜 구간의 앞부분은 단독 모듈로 채워 주기를 맞추고, 완전한 반복 묶음만 배치한다. 공유 패턴은 이후 후보의 필수 조건이며, 부족한 폭에서 다른 패턴으로 임의로 흔들지 않는다. 정면/측면이나 Region이 바뀌면 별도 배열이다.

## 연결 에셋과 조립 소유권

- 단독/왼쪽/오른쪽을 각각 한 칸 geometry로 제작했다. 일반 창, 쇼윈도, 업무용 큰 유리 세트가 있다.
- 왼쪽 유리는 로컬 x=+0.5까지, 오른쪽 유리는 x=-0.5부터 이어진다. 상하 프레임은 같은 높이/두께로 경계에 맞춰 끝나며 내부 세로 프레임은 없다. 유리 plane은 고정된 1/64 깊이로 배치한다.
- 각 묶음의 family·높이를 검증하며, 색상은 기존 성분/Seed palette를 공유한다. PY/NY로 돌리지 않고 네 벽 방향의 기존 u/v/n 기저를 사용한다.
- `middle` 연결 역할은 데이터 계약에 있지만 해당 에셋은 아직 없으므로 현재는 single 또는 left/right만 선택할 수 있다.
- 새 스타일은 단위 모서리 칸 확보 후 패턴을 배정한다. 새 Facade Trace가 있는 면은 **기존 2면 window corner 대체에서 제외**한다. 기존 스타일의 corner 규칙은 변경하지 않았다.
- 지붕/처마는 기존 조립을 유지한다. 새 상단 마감은 `kind=attachment`, `faceIds=[]`이며 구조 소유권을 차지하지 않는다. 최종 `validateAssembly`로 모든 외피의 구조 소유자가 정확히 하나인지 확인한다.

## 두 예시 스타일

| 구분 | 상가형 | 업무형 |
| --- | --- | --- |
| 정면 지상층 | 출입구 + 넓은 쇼윈도 묶음, 기단 | 로비 입구 + 큰 유리 묶음 |
| 측면 지상층 | 일반 단독 창/기둥 | 큰 단독 유리 |
| 반복층 (스타일 v2) | 양 끝 마감 + 균일한 일반 창, 홀수 폭 교대 기둥 | 양 끝 얇은 기둥 + 균일한 큰 유리, 홀수 폭 교대 기둥 |
| 모서리 | 두꺼운 모서리 기둥 | 얇은 pilaster |
| 노출 상단 | 두 줄 띠와 dentil 돌출 마감 | 단순 얇은 cap |

앱의 건축 스타일에서 두 예시를 선택한다. `Style gallery · 1층/2층/본동·별동` Fixture로 같은 스타일의 높이별 차이를 비교할 수 있다. Inspector에는 스타일/버전, 층 역할, 정면/측면, 패턴, 모듈, 연결 묶음/조각, 상단 경계, 후보 탈락/보충 이유를 표시한다.

## 저장과 검증

새 문서는 schema 4 / `building-patterns-v1`이며 `buildingDefinition` 전체를 저장한다. ID/버전만 저장하면 코드의 예시 데이터 수정으로 과거 사용자 파일의 결과가 바뀔 수 있으므로, 실제 사용한 정의도 함께 보존한다. 코드는 저장하지 않으며 타입/에셋/연결/문법 계약에 맞는 데이터만 수락한다. 기존 catalog/asset metadata는 등록 버전과 대조한다.

v1/v2/v3 Golden은 수정하지 않았다. 새 v4 Golden은 상가형·업무형 각각 독립 파일이다. 데이터 변경 후에도 이전 파일은 포함된 정의로 생성한다. 에셋 recipe와 해석기 자체의 변경에는 별도 algorithm/catalog 버전이 필요하다.

- `npm run verify`: Application/Core 타입 검사, 89개 테스트, production build.
- `tests/building-style.test.ts`: 1/2/5층, 별동/단차, 지면 조건, 정면 출입구, 폭 1~11, 구멍/문/모서리, 네 방향 접합, 반복층 정렬, 후보 순위, 실제 데이터 변경, 잘못된 묶음/크기, v4 저장과 이력, 새 Golden.
- 실제 geometry의 유리 경계 좌표가 네 방향에서 일치하고, 접합 위치에 내부 세로 프레임이 없는지 검사한다.
- `e2e/building-style.spec.ts`: 두 스타일의 연결 조각/층 역할/Trace, v4 사용자 정의, 직접 삭제와 Undo/Redo, 저장/복원, 실제 facade/height-gallery 스크린샷.
- `npm run test:e2e`: 기존 회귀를 포함한 **8개 시나리오 통과**. 실제 두 스타일의 facade 및 1층/2층/본동·별동 gallery 렌더를 열어 확인했다. 이미지 기록은 `test-results/building-style-*/`에 생성된다.

## 남은 한계

축 정렬 정수 Grid와 1×1 벽 모듈만 지원한다. 실제 도로·대지·보행 접근성, 경사/곡면 외벽, 임의 층고, 문자열 BDF DSL, 자동 모듈 stretching, 실내/관통 창, 3칸 이상 연결 에셋은 포함하지 않는다. 비다양체 진단이 있는 부피에서는 기본 벽으로 내려가고 고급 연결/마감을 보류한다. 좁은 구간이나 구멍에서는 창 배열보다 완전한 묶음과 정확한 coverage가 우선이다. 종전 CPU benchmark는 이전 버전의 측정값이며 새 스타일의 성능 측정값으로 주장하지 않는다.


## 스타일 v2: 끝 마감과 대칭 중앙 반복

2026-09-17 후속 요청으로 상가형/업무형의 기본 정의를 v2로 변경했다. 벽면 해석기와 geometry는 변경하지 않았다. `X`는 마감/기둥, `O`는 창문 한 칸이다.

- 끝 칸을 확보한 뒤 내부 짝수 폭은 `[left,right]`를 반복한다. 전체 폭 6은 `XOOOOX`다.
- 내부 홀수 폭은 `[single,pier]`를 반복하고 고정 `end=[single]`로 닫는다. 전체 폭 5는 `XOXOX`다. 마지막에 기둥이나 반쪽 연결 창문이 남지 않는다.
- 기존 정확한 폭/보충 수 우선 순위가 적합한 짝수/홀수 후보를 결정한다. 양 끝 마감은 반복부에 중복해서 넣지 않는다.
- 폭 3은 `XOX`, 폭 1~2는 단순 창문으로 내려간다. 지상층 출입구가 있는 구간이나 형태가 다른 층은 고정 문/실제 연속 구간/공유 배열 제약을 지키므로 위 도식과 달라질 수 있다.
- 기존 스타일 v1 정의와 저장 파일/Golden은 그대로 보존한다. v2 Golden은 `fixtures/golden-v4-style-v2/`에 따로 둔다.
- `Facade rhythm · XOOOOX / XOXOX` 예제와 두 스타일의 실제 렌더로 짝수/홀수 구성을 비교한다. 단위 테스트는 폭 3~10, 네 방향, middle/top 행의 X/O 위치를 정확히 검사한다.


## 스타일 v3: 짝수 폭 지상층 균형

기존 단일 중앙 출입구는 짝수 폭에서 왼쪽/오른쪽 잔여 구간이 한 칸 달라 서로 다른 창문 패턴을 만들었다. `entranceLayout=centered-parity`에서는 짝수 폭에 중앙 두 칸, 홀수 폭에 중앙 한 칸을 확보한다. 나머지 패턴 선택과 조립은 그대로 사용하며, 기본 v3 패턴은 양쪽의 동일 폭에 동일한 대칭 구성을 배정한다. 폭 2는 두 입구, 폭 4는 XDDX로 짧은 구간을 처리한다.

한 성분에 **하나의 출입구 구역**이라는 정면 정책을 유지하며 두 입구를 다른 벽면에 분산시키지 않는다. 각 입구의 Trace/Inspector에 entranceSpan과 중앙 대칭 근거를 표시한다. 문 모듈은 각각 한 칸이며 길게 늘이지 않는다. Custom 패턴 자체가 비대칭이면 이 정책은 좌우 가용 폭만 맞추며 에셋을 임의 반전하거나 재배열하지 않는다.

해석기의 새 정책이므로 새 문서는 `building-patterns-v2`로 명시한다. 필드가 없는 이전 정의는 `building-patterns-v1`을 유지하고 같은 출력을 재현한다. v1/v2 스타일의 기존 4개 v4 Golden을 입력부터 출력까지 재생하여 확인했고 새 스타일 v3의 Golden은 별도 생성했다.

검증: 폭 1~6/13~16, 네 벽 방향에서 출입구 위치·개수와 창문/마감/연결 조각의 반사 대칭을 검사한다. 14→13칸 삭제 후 입구 2→1 전환 및 Undo/Redo 복원을 검사한다. 브라우저에서 두 스타일의 14칸 예제와 중앙 두 입구 Trace/실제 렌더를 확인한다. 전체 타입/89개 테스트/build와 브라우저 회귀를 수행했다.
