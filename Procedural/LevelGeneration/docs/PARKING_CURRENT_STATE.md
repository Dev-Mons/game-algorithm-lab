# 현재 주차장 알고리즘 진단

분석일: 2026-09-25. 코드 기준: `abb1d0318226b4913c78679db8c8008289ddf0c2`. 로컬 main과 현재 워크트리가 같은 커밋임을 확인했다. 제품 코드·baseline·로컬 main은 수정하지 않았다. 진단용 복사본과 실행 산출물만 만들었다.

**판단: 지상 주차의 배치 후보 생성·선택은 재설계할 근거가 충분하다. 기존 충돌·예약·차량/보행 검증까지 전부 폐기할 근거는 없다. 개방형 주차 건물은 별도의 외형 프로토타입으로, 지상 주차 계획과 연결되어 있지 않다.**

## 1. 현재 두 시스템

| 구분 | 지상 주차 영역 | 개방형 주차 건물 |
|---|---|---|
| 입력 | `sceneInputs.parkingAreas`: ID, Y=0 셀 마스크, 보존 anchor | 건물 부피와 `parking` building rule |
| 생성 | 출입구 → 차로/보행 띠 → 구획 후보 → 진입/출차/보행 proof | 셀마다 슬래브·주차 줄, 일정 간격 기둥, 최상단 데크 |
| 실제 출력 | 승인된 1×2 구획, 차로/보행 포장, 출입 화살표, 경로/예약/사유 | 데크·기둥·줄 표시 ScenePlacement |
| 이동 | 지상 `grid-car-v1` 모델의 검증 경로 | 차량 출입·층간 경사로·상층 경로 없음 |
| 공간 | 원본 점유·다른 예약·도로와 함께 검증 | 외형이 개방되어도 원본 셀 합집합 전체를 solid로 예약 |

근거: [parking-rule.ts](../src/core/parking-rule.ts), [rule-spatial-adapters.ts](../src/core/rule-spatial-adapters.ts), [spatial-analysis.ts](../src/core/spatial-analysis.ts), [parking-placement.ts](../src/core/parking-placement.ts).

4×3×4 건물 예제를 실제 생성했을 때 원본 48셀, 바닥 데크48·지붕 데크16·기둥12·주차 줄48개가 나왔다. 지상 주차 영역과 검증된 구획은 0개다. **줄48개를 주차48대로 해석하면 안 된다.** [실제 화면](parking-current-evidence/parking-building-no-access-proof.png).

## 2. 지상 생성 흐름과 제약

```text
주차 원본 마스크
  → 도로·solid 제외 / 4방향 연결 성분
  → 경계의 도로 출입 후보: 정렬 후 최대 4개
  → 성분마다 X 또는 Z 축 + 0..8 위상의 18개 띠 패턴
  → 출입구에서 각 차로 띠를 연결
  → 보행 crossing 인증 / 차량 왕복 연결 / 예약 승인
  → 후보 구획 수가 많은 배치 선택
  → 건물 출입구 계획
  → 선택된 배치의 각 구획 진입·출차·뒤쪽 보행 접근 검증
  → 탈락 구획 제거 / 포장·줄·화살표 출력
```

기본 치수는 [environment-settings.ts](../src/core/environment-settings.ts)에 고정되어 있다: 차로4칸, 구획1×2칸, 보행 띠1칸, 도로 연결 거리 최대4칸, 출입구 최대2개. 반복 주기는 `4+5=9`칸이다. 사용자에게 세부 설정 UI를 추가한 상태가 아니다.

[parking-circulation.ts](../src/core/parking-circulation.ts)의 핵심 제한:

- 출입구는 연결 거리·경계 길이·숫자 좌표 순으로 정렬한 뒤 **첫 4개만** 남긴다. 한쪽 끝의 인접 후보가 네 자리를 차지할 수 있다.
- 성분 전체가 하나의 X/Z 방향과 하나의 위상을 공유한다. ㄱ/U자의 날개마다 다른 주차 방향, 지역별 한쪽/양쪽 주차, 여러 종류의 연결 차로를 조합하는 생성기는 없다.
- 각 띠에 대한 차로 연결과 대표 상태의 왕복 증명이 실패하면 그 배치 후보를 거절한다. 부분적으로 활용할 수 있는 지역을 별도 배치 문제로 나누는 기능은 제한적이다.
- 출입구 두 번째 추가는 256셀 이상, 거리 조건, 최대 출차 거리 4전이 이상 개선 조건이 있다. 최초 배치의 축/위상/차로를 유지하는 후처리다.
- 정적 배치 선택은 `trial.potential`(차로 확정 후 남은 후보 구획 수), 미사용 셀, 추가 차로 크기 순이다. **최종 구획 proof를 통과한 대수를 직접 최적화하지 않는다.** 입구 예약과 구획 proof는 후속 단계에서 수를 줄일 수 있다.
- `PROVEN_POTENTIAL_DOMINATED` 가지치기도 후보 구획 수를 기준으로 한다. 현재 검색 공간 밖의 배치나 최종 주차 대수의 전역 최적성을 보장하지 않는다.

부모 주차 영역당 논리 예산은 차로1,500,000·구획500,000·배치시도128이다. 구획 proof 예산을 먼저 보호하고, 성분별로 예산을 나눈다. 수치 변경만으로 생성 패턴의 표현 범위가 늘어나는 구조는 아니다.

## 3. 확인된 기능 결함: 한 칸 삭제 → 18대가 0대

원본: 12×12 마스크, Z=-4..-1의 인접 도로, Seed42, anchor0. 정상 결과는 18대다. 마스크에서 `(5,0,5)` 한 칸만 제외하면 143셀 전체가 유지되지만 **0대, `TURN_SWEEP_BLOCKED`**가 된다.

실제 브라우저에서도 그 칸을 클릭해 Q로 삭제했고 동일한 결과가 나왔다. Ctrl+Z로 복원하면 18대가 돌아온다. [삭제 전](parking-current-evidence/R12-before.png) · [한 칸 삭제 후](parking-current-evidence/R12-single-hole-zero-stalls.png) · [브라우저 기록](parking-current-evidence/browser-report.json).

원인을 구분하기 위해 제품 소스를 변경하지 않고 진단용 복사본에서 **출입구 후보 상한만** 바꾸었다. 예약, 차량 모델, 차로 연결과 최종 구획 proof는 원래 함수를 그대로 사용했다.

| 출입구 후보 상한 | 승인 구획 | 선택된 출입구 | 실제 시도 수 | 논리 차로 작업 수 |
|---|---:|---|---:|---:|
| 현재 4 | 0 | 없음 | 72 | 7,026 |
| 진단용 8 | 6 | `(5..8,0,0)` | 48 | 8,931 |
| 진단용 16 | 6 | 같음 | 54 | 9,447 |
| 진단용 64 | 6 | 같음 | 54 | 9,447 |

[원시 대조 결과](parking-current-evidence/gate-counterfactual.json). 상한 변경에 따라 배치 후보 수/시도 가능 수도 달라지지만 같은 부모 논리 예산 안에서 원래 검증을 통과했다. **현재 0대 결과는 공간의 불가능성을 입증하지 않는다. 후보 제한 때문에 가능한 6대 배치를 놓친 것이다.** 6대가 최댓값이라는 뜻은 아니다.

출입구 후보를 늘려도 아래 U자7대·폭6 긴 부지4대는 개선되지 않았다. 이 문제는 단순 상한 조정만으로 끝나지 않는다.

## 4. 실제 배치 품질

모든 크기는 입력 셀 기준이다. 모든 구획은 현재 1×2 모델이므로 구획 면적 비율은 `2×승인 대수/유효 셀`이다. 현실의 적정 주차장 효율 기준과 비교한 수치가 아니다.

| 입력 | 유효 셀 | 승인 대수 | 구획 면적 | 차로 면적 | 보행 전용 면적 | 특징 |
|---|---:|---:|---:|---:|---:|---|
| 6×6 | 36 | 0 | 0% | 55.6% | 44.4% | 전부 통로로 배정되고 구획 없음 |
| 12×12 | 144 | 18 | 25.0% | 30.6% | 34.7% | 정형 예제에서는 작동 |
| 30×20 | 600 | 96 | 32.0% | 42.7% | 24.0% | 넓은 직사각형에서는 다수 배치 |
| ㄱ자16×16, 날개8 | 192 | 19 | 19.8% | 31.2% | 31.8% | 한 축 패턴, 잔여 공간 |
| U자16×16, 날개6 | 216 | 7 | 6.5% | 34.7% | 38.0% | 큰 통로와 길게 남는 미배치 부분 |

[ㄱ자 화면](parking-current-evidence/L16.png) · [U자 화면](parking-current-evidence/U16-arms6.png) · [폭6 부지 화면](parking-current-evidence/rect-6x16.png) · [27개 사례 결과](parking-current-evidence/report.json).

위 표만으로 각 마스크의 최적 주차 대수를 계산한 것은 아니다. 고정 차로 폭/차량 회전 모델 자체의 보수성도 결과에 영향을 준다. 작은 부지와 오목한 부지에 현재 생성 방식의 제약이 크게 드러난다는 관찰이다.

추가로 R12/U16/L16/16×16에서 현재의 네 출입 후보와 18개 띠 패턴을 각각 최종 구획 proof까지 평가했다. **그 네 표본의 같은 후보 집합에서는 현재보다 많은 대수를 가진 안을 찾지 못했다.** 따라서 후보 구획 수에 의한 점수화는 설계 한계로 구분하며, 이번에 확인한 주원인을 그 점수화의 실측 오류라고 주장하지 않는다. [점수화 대조](parking-current-evidence/score-counterfactual.json). 이 오프라인 비교는 전체 시도의 runtime 예산 준수나 전역 최적성을 증명하지 않는다.

## 5. 유지할 가치가 있는 부분

- 원본 셀·구멍·다른 객체의 점유와 Box16 예약을 보존한다. batch 예약과 우선순위, 인증 crossing이 있어 장식 표시를 실제 통과 가능성으로 잘못 사용하지 않는다.
- [vehicle-motion.ts](../src/core/vehicle-motion.ts)의 차량은 뒤 셀+방향으로 1×2 footprint를 가지며, 전후진 및 90도 회전/역회전의 4×4 sweep을 검사한다. 실제 차체/연속 조향 물리 모델은 아니다.
- [parking-stalls.ts](../src/core/parking-stalls.ts)는 도로+확정 차로+자기 두 셀만 사용한다. 다른 주차 구획을 비워 둔다고 가정하지 않는다. 진입·출차 양쪽 경로와 뒤쪽 보행 접근을 확인하고 실제 전이를 재검사한다.
- `VehicleDomain`은 실행 내 셀/상태/전이 비트 인덱스를 재사용한다. base graph1회·BFS2회와 구획당 추가 상태16 이하의 검사 방식은 검증 비용을 제한한다.
- 입력/계획 분리, 보존 anchor, 결정론, Undo/Redo/JSON, 미배정 이유, 예산 보호는 새 생성기도 유지해야 한다.

보존 대상이 있다고 해서 치수와 grid-car-v1이 새 게임 목표에 항상 맞다는 뜻은 아니다. 차량 스케일·최소 회전 여유는 새 설계에서 별도로 결정할 계약이다. 현재 경로의 시작은 출입구 앞 `roadStates`다. 도시 전체의 출발지부터 실제 주행이나 상층 이동을 검증한 결과가 아니다.

## 6. 진단/표시의 한계

한 칸 구멍 사례에서도 전체 상태는 `OK`, `parkingCirculation/parkingStalls: ready`, 주차 요약은 검증0대·미검증0개로 표시된다. 이는 실행 완료와 최종 생성된 구획 검사 결과다. **모든 배치 가능성을 조사했거나 사용 가능한 주차장이 완성됐다는 뜻이 아니다.**

`parkingQuality.untestedStalls`는 현재 항상0으로 구성되며 최종 선택된 구획 집합 밖의 미탐색 출입구/배치를 세지 않는다. 초기 후보 상한으로 빠진 출입구 수도 설명되지 않는다. 후속 설계에서는 `공간상 불가능`, `지원하지 않는 배치`, `후보 탐색에서 못 찾음`, `예산으로 미검사`를 분리할 필요가 있다.

## 7. 재설계 경계 제안

**교체 중심:** `parking-circulation.ts`의 출입 후보 생성, 부지 분해, 차로/구획 배치 후보, 후보 평가 순서.

1. 도로 frontage별로 분산된 출입 후보를 만들고 원거리/반대편 가능성을 좌표 순서에서 잘라내지 않는다.
2. 부지를 차량이 통과 가능한 지역과 연결부로 해석하고, 지역별 축·한쪽/양쪽 구획과 연결 차로를 조합한다. 한 성분 전체를 9칸 줄무늬 하나로 덮지 않는다.
3. 실제 검증된 구획 수, 통로/잔여 면적, 접근 거리, 영향을 받지 않은 구획의 유지 여부를 함께 평가한다. 탐색의 완결성 수준도 출력한다.
4. 원본 점유·예약·차량/보행 검증과 원자적 수락은 재사용한다. 새 목표에 따라 차량 치수를 바꾼다면 검증 모델도 명시적으로 버전/계약을 정한다.
5. 다층 주차장이 목표라면 외형 규칙부터 늘리지 않고 층별 설치 가능 바닥·기둥·경사로/연결 그래프와 실제 주차 계획을 먼저 정의한다. 현재 solid 셀 모델과 장식 데크를 그대로 합쳐 해결할 수 있는 단계가 아니다.

지금은 현황 분석 요청이므로 위 재설계를 제품 코드에 적용하지 않았다.
