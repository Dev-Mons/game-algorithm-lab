# LevelGeneration 동작 룰 개발 가이드

이 가이드는 **어떤 입력을 배치하면 무엇이 생성되고, 주변 조건에 따라 어떻게 달라지는지**를 설명한다.
현재 코드로 구현된 동작을 기준으로 하며, 새 기능 개발·수정 시 유지해야 할 조건과 예외를 함께 적었다.
정확한 수식·데이터 형식·에셋 계약은 [생성 규칙 명세](GENERATION_RULES.md), 다른 엔진에서의 구현은
[네이티브 이식 가이드](NATIVE_PORTING.md)를 따른다. 영상에서 관찰한 미확정 동작은
[영상 참조 연구](VIDEO_RULE_STUDY.md)에서 구분한다.

## 먼저 알아둘 생성 방식

사용자는 건물 부피, 도로, 인도, 주차 영역, 오브젝트 설치 의도를 입력한다.
생성기는 그 입력의 실제 외피·지지면·주변 도로·사용 가능한 공간을 분석하여 외벽과 시설을 결정한다.
예제에 들어 있는 층수나 형태는 시작 입력이며, 모든 건물에 강제되는 룰이 아니다.
Y는 높이이고 지상 도로·인도·주차 입력은 Y=0이다. 아래의 폭·높이·거리는 별도 표시가 없으면 셀 단위다.

| 입력 또는 주변 조건 | 대표 결과 |
|---|---|
| 좁은 인도를 두 도로 사이에 배치 | 조건을 만족하면 교통섬과 화단·연석 |
| 건물 주변에 보행으로 연결되는 도로 배치 | 도로 접근이 가능한 입구 후보를 우선 선택 |
| 건물 높이·컨셉 변경 | 저층·중간층·상층의 구간과 외벽 패턴 재계산 |
| 건물 일부를 낮추거나 후퇴시킴 | 실제 노출 상면과 그 위치의 옥상 벽·마감 |
| 도로를 ㄱ자·T자·십자로 연결 | 실제 연결 모양에 따른 교차부와 접근 방향의 도로 표시 |
| 지상에 주차 영역 배치 | 차로·진입·출차·보행이 검증된 구획만 채택 |
| 같은 시설 입력을 옥상·도로변·교통섬에 배치 | 설치 문맥에 따라 설비·거리 시설·볼라드 등으로 변화 |
| 설치 오브젝트의 지지 건물을 제거 | 지지 없는 열의 생성 제외, 원본 입력과 진단 보존 |

계산 순서는 **부피/관계 분석 → 수직 구간과 필수 공간 → 주차 차량 동선 → 건물 입구/보행 →
최종 주차 구획 → 필수 외피/시설 → 선택 마감**이다. 외벽에서 문을 먼저 그린 뒤 접근 경로를
맞추는 식으로 순서를 뒤집으면 안 된다.

## 1. 도로 사이에 인도를 놓으면 교통섬이 생긴다

교통섬은 별도 입력 종류가 아니다. 인도 마스크를 X/Z 4방향 연결 성분으로 나누고,
각 성분과 주변 도로의 관계로 일반 인도 또는 교통섬을 결정한다.

| 연결된 인도 영역의 조건 | 판정 |
|---|---|
| 도로와 닿은 변이 없음 | 일반 인도 |
| 영역의 한 칸이라도 지상 건물 또는 주차 마스크에 덮임 | 성분 전체를 일반 인도로 유지 |
| 바깥 변이 모두 도로이고 면적이 24셀 이하 | 교통섬 (`ENCLOSED_BY_ROADS`) |
| +X/−X 또는 +Z/−Z 양쪽에 도로가 있고, 해당 축의 최장 연속 길이가 3셀 이하 | 교통섬 (`BETWEEN_ROADS`) |
| 위 조건을 만족하지 않음 | 일반 인도 |

양쪽 도로 조건은 **성분 전체가 접하는 방향**으로 센다. 모든 인도 칸이 양쪽 도로와 직접 접해야 하는 것은 아니다.
폭 검사도 외접 박스 크기가 아니라 해당 축의 최장 연속 셀 길이를 사용한다.
완전히 둘러싸인 면적 조건을 먼저 평가하므로, 4×4 인도도 둘레가 모두 도로면 교통섬이 된다.

```text
평행 도로 사이의 인도 예시 (위에서 본 모습)
R R R R R R R R     R: 도로
. S S S S S S .     S: 인도, .: 빈 지면
R R R R R R R R
→ 양 끝이 열려 있어도 두 도로 사이 폭이 1셀이므로 교통섬
```

교통섬은 바깥 둘레에 연석, 내부에 화단 표시를 만든다. 일반 인도는 도로와 닿는 변에만 연석을 만든다.
섬 위의 지상 오브젝트는 중앙분리대 문맥으로 해석한다. 시설 입력은 안전 볼라드,
높이 1셀 식생 입력은 중앙분리대 화분으로 바뀔 수 있다. 화단 표시 자체가 나무 입력을 추가하지는 않는다.

**개발 시 확인할 예외:** 한쪽에만 도로가 있는 인도, 평행 도로 사이 폭 4셀 인도,
도로로 둘러싸인 6×6 인도는 일반 인도다. 건물·주차 덮임 여부와 면적/폭의 판정 순서를 유지한다.
도로를 제거하거나 인도 성분을 합치면 판정도 다시 계산한다.

구현: [sidewalks.ts](../src/core/sidewalks.ts). 기존 사례: [sidewalks.test.ts](../tests/sidewalks.test.ts).

## 2. 인도와 도로는 한 칸을 공유하지 않는다

편집에서 도로와 인도 중 나중에 칠한 입력이 그 칸을 소유한다. JSON 입력에서 둘이 겹치면 검증 오류다.
인도는 건물·주차·오브젝트와 공존할 수 있고, 건물·주차 아래의 포장만 숨긴다.
건물을 제거하면 보존된 인도가 다시 보인다.

인도 표면 높이는 2/16셀이다. 인도 위 지상 오브젝트에는 표시용 높이 오프셋을 적용하지만,
원본 좌표·충돌 예약·보행 그래프는 그대로다. 현재 인도 추가만으로 건물 입구나 주차 접근 증명이 바뀌지 않는다.

구현: [scene-inputs.ts](../src/core/scene-inputs.ts), [sidewalks.ts](../src/core/sidewalks.ts).

## 3. 건물 문은 도로로 접근할 수 있는 외벽을 우선한다

“도로 방향에 문이 생긴다”는 **문 앞에서 실제로 도로까지 걸어갈 수 있는 후보를 우선한다**는 뜻이다.
가장 가까운 도로를 향해 문을 무조건 붙이거나 모든 도로변에 문을 만드는 규칙은 아니다.
문 바로 바깥에 유효한 발판이 있어야 하고, 경로는 장애물·예약·몸체 여유 공간 검사를 통과해야 한다.
도로까지의 보행 경로 한도는 24셀이다.

입구 후보는 지상 외벽의 실제 연속 구간에서 폭 1 또는 2셀로 만든다.
길이 3셀 이상 외벽에서는 양 끝 칸을 후보에서 제외한다. 짧은 1~2셀 외벽에도 폭 1셀 입구는 가능하다.
지원하지 않는 외벽 형태, 기둥 면, 맞는 문 에셋이 없는 위치, 발판이 도로 자체인 위치,
충돌하는 위치는 후보에서 탈락한다.

주 입구의 선택 순서는 다음과 같다.

1. 도로 접근 가능 여부.
2. 집 예제라면 원본 문 위치 선호 여부.
3. 짧은 보행 경로 → 긴 외벽 구간 → 넓은 문 → 구간 중앙에 가까운 위치.
4. 컨셉의 고정 방향 순서와 좌표 순서로 동점 해소.

건물 규모와 검증된 입구 후보 면의 수에 따라 최대 4개까지 만든다. 추가 입구는 다른 도로 접근부·다른
외벽면·기존 입구와의 거리를 고려하며 최소 간격 4셀을 지킨다. 큰 건물이어도 유효 후보가 없으면
목표 개수를 채우지 못할 수 있다. 외벽 패턴은 확정된 문 면을 받아 그 위치를 창문으로 덮지 않는다.

```text
가능한 지상 배치: [건물 외벽/문] [빈 발판] [도로]
탈락하는 배치:   [건물 외벽/문] [도로]
```

**도로가 없어도 문은 생길 수 있다.** 유효하고 비어 있는 지상 발판이 있으면 로컬 입구 1개를 만들 수 있다.
이때 `access: local`이며 도로 대상이나 보행 경로를 꾸며내지 않는다.
반대로 건물에 도로를 바짝 둘러 발판을 없애거나 건물을 지상에서 띄우면 입구가 생성되지 않을 수 있다.
도로가 가까워도 장애물이 경로를 막으면 다른 후보 또는 로컬 입구가 선택될 수 있다.
현재 문 생성은 실내 통로나 문 애니메이션을 제공하지 않는다.

구현: [entrance-plan.ts](../src/core/entrance-plan.ts), [access-graph.ts](../src/core/access-graph.ts).
기존 사례: [entrances.test.ts](../tests/entrances.test.ts).

## 4. 건물은 저층·중간층·상층을 같은 패턴으로 채우지 않는다

먼저 수직 구간을 정하고 각 구간의 창·벽·띠 에셋을 선택한다. 같은 구간 안에서도 첫 행(`foot`),
중간 행(`repeat`), 마지막 행(`head`), 한 행뿐인 구간(`single`)을 구분한다.
위쪽에 같은 방향 외벽이 없는 면에는 별도 끝 마감(`cap`)을 적용한다.

| 컨셉 | 수직 동작과 외형 |
|---|---|
| A / shop | 저층·중간층·상층을 구분. 밝은 수평 띠와 어두운 연속 창 |
| B / office | 저층·중간층·상층을 구분. 브론즈 창과 구간 경계의 불투명 벨트·흰 코너 기둥 |
| C / urban-shop | 저층 retail·중간 office·상부 upper, 높이 12 이상이면 mechanical 추가. 높은 저층 창과 지역별 구간 |
| D / tower11-d | 저층 1 + 나머지 중간층. 별도 crown 구간은 없지만 지상 창·상부 옥상 벽 변형을 구분 |
| 집 컨셉 | A~D의 층별 띠 대신 주택 벽·창·문·지붕 모듈을 조립 |

예를 들어 A 높이 8셀은 **저층 2 + 중간 5 + 상층 1**, B 높이 16셀은 **저층 3 + 중간 10 + 상층 3**이다.
A/B 높이 1~3셀은 저층 1과 남은 중간층만 만들며 상층을 억지로 끼워 넣지 않는다.
건물 높이를 바꾸면 구간을 다시 배분하므로 편집한 층 외의 외벽도 바뀔 수 있다.

**상층 구간과 옥상은 서로 다른 판정이다.** D처럼 상층 구간이 없는 건물도 옥상은 있고,
낮은 날개의 꼭대기가 전체 건물의 중간층 구간에 속해도 그 위치의 옥상 마감을 가질 수 있다.
컨셉 변경은 사용자 부피를 자동으로 깎거나 예제 층수로 바꾸지 않는다.

구현: [vertical-design.ts](../src/core/vertical-design.ts), [vertical-allocation.ts](../src/core/vertical-allocation.ts),
[building-style.ts](../src/core/building-style.ts). 기존 사례: [vertical-design.test.ts](../tests/vertical-design.test.ts).
정확한 배분은 [높이 규칙](GENERATION_RULES.md#높이-규칙)을 따른다.

## 5. 낮은 날개와 높은 몸체의 처리 방식은 컨셉에 따라 다르다

A/B/D는 연결된 건물 성분 전체의 높이를 기준으로 구간을 정한다.
예를 들어 A의 12셀 몸체와 연결된 4셀 날개는 몸체 기준 구간을 공유하고,
날개의 끝에는 실제 노출 경계에 맞는 옥상/끝 마감을 적용한다.

C는 같은 최상단 높이를 가진 인접 X/Z 열을 지역으로 묶어 저층·중간·상부 구간을 재평가한다.
지역 면적 4셀 이상, 짧은 폭 2셀 이상, 바닥부터 꼭대기까지 높이 2셀 이상인 조건을 사용한다.
조건을 만족하지 않는 열은 성분 전체 구간을 쓴다. 따라서 C의 낮은 날개와 높은 몸체는 각각 상부 구간을
가질 수 있다. 모든 컨셉에 C의 지역 규칙을 일괄 적용하면 기존 결과가 달라진다.

구현: [mass-relations.ts](../src/core/mass-relations.ts), [vertical-design.ts](../src/core/vertical-design.ts).

## 6. 옥상은 건물 전체의 최고층에만 생기는 것이 아니다

외피는 실제 셀 점유에서 구한다. 수평 노출 상면은 성분 최고 높이면 `roof`, 그보다 낮으면 `terrace`로
분류한다. 수직 외벽의 `wallKind: rooftop`은 **전체 입력의 같은 X/Z 열에서 가장 높은 셀의 벽**에 붙는다.
낮은 날개·계단형 매스·후퇴부에도 적용되며, 같은 열 위에 다른 부피가 있으면 옥상 벽으로 취급하지 않는다.
단순히 해당 외벽이 그 자리에서 끝났다는 `cap` 판정과도 다르다.

옥상 벽 변형에는 난간/상부 마감이 포함된다. 일반 건물에서 난간은 수평 지붕에 별도 장식으로
무조건 추가하는 것이 아니라 그 수직 호스트 면의 에셋에 포함한다.
선택 마감은 실제 경계와 예약 충돌을 검사하며, 들어갈 공간이 없으면 그 마감만 생략할 수 있다.
빈 부분을 직육면체 외피로 덮거나 덮인 테라스에 옥상 난간을 강제로 붙이지 않는다.

구현: [analysis.ts](../src/core/analysis.ts), [facade-face-selection.ts](../src/core/facade-face-selection.ts),
[facade-trims.ts](../src/core/facade-trims.ts).

## 7. 창문 반복은 벽의 실제 길이·구멍·코너를 따른다

가로 패턴은 A/B 3셀, C 2·3·4셀 중 선택된 주기, D 1셀을 기본으로 한다.
절대 좌표와 보존된 건물 anchor로 위상을 맞춘다. 벽을 늘렸다는 이유만으로 모든 기존 창의 시작점을
새 최소 좌표로 재설정하지 않는다.

벽에 구멍이 있거나 문·시설·기둥이 선점한 면, 수직 구간·행 역할·옥상 여부·끝 경계가 바뀌는 곳에서는
반복을 끊는다. 좌우 연결 창은 완전한 쌍으로만 만들고 짧은 나머지는 독립 모듈로 채운다.
볼록 코너는 실제 이웃 외벽의 노출로 판정하며 오목 코너에 볼록용 에셋을 붙이지 않는다.

A~D의 사용자 외벽 타일 설정은 저층·중앙·상층·코너를 바꿀 수 있다. 코너 설정이 있으면 구간 설정보다
우선하며, 문·시설 벽·기둥·다층 프레임은 교체하지 않는다. 옥상·끝 마감·코너 형상 판정도 유지한다.

구현: [facade-layout.ts](../src/core/facade-layout.ts), [facade-fitting.ts](../src/core/facade-fitting.ts),
[facade-face-selection.ts](../src/core/facade-face-selection.ts).

## 8. 도로 모양과 표시는 실제 연결된 셀에서 결정한다

도로 마스크에서 진행 축과 단면 폭을 구하고, 두 축으로 뻗는 띠가 실제로 만나는 곳을 교차부로 분석한다.
바깥으로 이어지는 방향이 2개면 ㄱ자, 3개면 T자, 4개면 십자다.
부분 폭 접속이나 옆 접촉은 전이 구간으로 표시하며 완전한 교차로로 자동 승격하지 않는다.
표시용 모듈 분할선에는 외곽선이나 새 교차로를 만들지 않는다.

폭 2 이상 직선에는 중앙 이중 황색선, 폭 4 이상에는 추가 백색 점선을 표시한다.
폭 1에서는 과밀 표시를 생략한다. 교차부 중앙은 비우고 폭 2 이상 실제 연결 입구의 접근부에
횡단보도·정지선을 둔다. 표시가 원본 도로 밖으로 나가거나 짧은 구간에서 다른 접근 표시와 겹치면
해당 표시 묶음을 생략한다. 외곽선은 실제 노출 변에만 그린다.

횡단보도 그림이 있다고 보행·차량 교차가 인증된 것은 아니다. 도로 폭도 실제 법적 차로 수를 뜻하지 않는다.
현재 도로 분석은 교통 신호·차량 흐름 시뮬레이션을 제공하지 않는다.

구현: [roads.ts](../src/core/roads.ts). 기존 사례: [road-topology.test.ts](../tests/road-topology.test.ts).

## 9. 주차 영역은 들어가고 나올 수 있는 구획만 주차 대수로 인정한다

지상 주차 마스크에서 고정 장애물·도로·기존 예약을 제외하고 폭 4셀 차로, 1×2셀 구획,
보행 접근이 들어가는 배치를 찾는다. 부지 모양에 따라 양쪽 주차열·한쪽 주차열·혼합 방향 배치를 비교한다.
건물 입구 계획을 반영한 뒤 최종 구획마다 도로 출입구에서의 진입·출차·보행을 검증한다.

다른 구획이 비어 있다고 가정해서 그 구획을 통로로 사용하지 않는다.
차량 회전에는 4×4셀 sweep을 사용하므로 선으로 연결되어 보이는 좁은 길도 실패할 수 있다.
보행과 차로가 교차하면 별도 crossing 인증이 필요하다. 차로를 주차 마스크 밖으로 확장하지 않는다.
구획 뒤 보행은 검사에 통과한 실제 빈 지면을 사용할 수 있다.

주차열 끝의 남는 공간에는 충돌 없는 조경 섬을 만들 수 있다. 이는 1절의 인도 기반 교통섬과 별도 결과다.
최종 대수는 `quality.acceptedStalls`로 읽는다. 탐색 후보 수나 외형으로 그린 줄 수를 대수로 쓰지 않는다.
출입구는 최대 2개이고 두 번째는 대수를 늘리거나 같은 대수에서 출차 전이를 충분히 줄일 때 채택한다.
탐색 예산이 끝나면 미검증/미시도 상태를 남기며 전역 최적 배치라고 표시하지 않는다.

개방형 주차 **건물**은 슬래브·기둥·줄을 만드는 외형 프로토타입이다.
상층 경사로·층간 주행이나 지상 구획의 차량 증명이 적용되었다고 해석하지 않는다.

구현: [parking-layout.ts](../src/core/parking-layout.ts), [parking-circulation.ts](../src/core/parking-circulation.ts),
[parking-stalls.ts](../src/core/parking-stalls.ts). 기존 사례: [parking-layout-v2.test.ts](../tests/parking-layout-v2.test.ts).

## 10. 시설 종류는 설치 위치와 높이에서 결정된다

시설·조명·식생은 사용자가 입력한 설치 의도에서 생성한다. 도로를 놓았다는 이유만으로 주변 모든 칸에
시설을 자동 추가하지 않는다. 칠한 시설/조명 칸은 독립 슬롯이며 간격 규칙만으로 다른 칸을 비우지 않는다.

일반 시설의 문맥 우선순위는 외벽/조명 → 주차 구역 → 옥상 → 중앙분리대 → 식생 근처 → 도로변 →
광장 → 벽 앞 설비 → 기본 설비다. 여러 조건을 동시에 만족하면 이 순서로 결정한다.

| 설치 의도와 위치 | 대표 결과 |
|---|---|
| 조명 | 지상·옥상은 기둥 조명, 외벽은 벽 조명 |
| 주차 출입구 주변 시설 | 차단기 기둥·정산기 |
| 주차열 끝 또는 교통섬 시설 | 안전 볼라드 |
| 옥상 시설 열 높이 1 | 실외기, 같은 높이 건물 셀이 이웃하면 벽을 등진 환기구 |
| 옥상 시설 열 높이 2 / 3 / 4 이상 | 물탱크 / 격자 탑 / 안테나 |
| 식생 3셀 이내 시설 | 절대 접선 좌표 리듬에 따른 휴식 시설 |
| 도로 2셀 이내 시설 | 벤치·휴지통·자전거 거치대, 연석 줄의 소화전 리듬 |
| 도로 6셀 이내 광장 시설 | 화분·벤치·휴지통 격자 |
| 그 밖의 벽 앞 / 나머지 시설 | 설비함·실외기 / 설비함 |

시설 종류의 리듬은 절대 좌표·seed·외부 문맥을 사용한다. 옆 칸을 추가로 칠해서 기존 칸의 종류를
재추첨하지 않는다. 실제 본체와 보호 공간이 충돌하면 후보를 탈락시키고 이유를 남긴다.
모든 본체 배치 후 사용/유지보수 접근을 다시 검사한다. 접근이 미검증이라는 이유로 명시 입력을
자동 이동시키지 않는다.

외벽의 자동 시설은 연속 열 높이 1이면 지상에서 차양, 지상 위에서 발코니다.
높이 2 이상이면 지면에 닿는 열은 엘리베이터, 닿지 않는 열은 비상계단이다.
이 외형이 실제 승강·계단 이동을 증명하지 않는다. 기존 JSON의 명시 시설 종류는 우선한다.

구현: [fixture-plan.ts](../src/core/fixture-plan.ts), [fixture-catalog.ts](../src/core/fixture-catalog.ts),
[wall-facilities.ts](../src/core/wall-facilities.ts). 기존 사례: [fixture-plan.test.ts](../tests/fixture-plan.test.ts).

## 11. 식생과 시설에는 실제 지지면이 필요하다

지상 설치는 Y=0, 옥상 설치는 실제 노출 상면, 외벽 설치는 실제 외벽을 지지로 사용한다.
외벽에는 조명·시설을 설치할 수 있고 식생이나 아래쪽 면 설치는 지원하지 않는다.
호환되는 연속 수직 입력 열은 편집 fragment가 나뉘어 있어도 하나의 설치 높이로 해석한다.

식생은 높이 1이면 지상의 관목·옥상 화분·중앙분리대 화분을 문맥에 따라 선택한다.
높이 2 이상 열은 아래 줄기·중간 수관·꼭대기 수관 모듈로 나무를 만든다.
유효 식생 입력의 실제 셀은 고정 장애물로 예약하므로 주변 접근 계획에도 영향을 준다.

지지 건물을 지우면 지지를 잃은 열만 생성에서 제외한다. 원본 입력과 이유는 남겨 복원·진단할 수 있게 한다.
바닥이나 벽이 없어졌는데 공중의 메시만 유지하거나, 이동 가능한 계단 연결을 가정하면 안 된다.

구현: [scene-relations.ts](../src/core/scene-relations.ts), [scene-inputs.ts](../src/core/scene-inputs.ts).
기존 사례: [scene-relations.test.ts](../tests/scene-relations.test.ts).

## 12. 집은 주택 모듈로 조립하고, 작은 주차 영역은 부속 차고가 될 수 있다

집 컨셉은 실제 Blender에서 추출한 벽·문·창·지붕 모듈을 사용한다.
예제와 같은 부피는 이동/90도 회전해도 예제 지붕 조립을 사용한다. 다른 부피는 실제 노출 상면에
박공 띠를 조립하며, 별도 차고 컨셉의 자유 부피는 평지붕이다.
집 문도 공통 입구 검사를 통과해야 하므로 원본 예제의 문 위치가 막히면 다른 유효 면으로 바뀔 수 있다.
예제의 정원·차량·현관 계단·차양·굴뚝 같은 부속물을 자동 복사하지 않는다.

별도 차고 컨셉을 제외한 집에 붙은 주차 성분이 다음 조건을 만족하면 부속 차고로 해석한다.

- 지상 직사각형, 면적 2셀 이상, 각 축 크기 최대 4셀, 출입 방향 깊이 2셀 이상.
- 한 외벽 변 전체가 같은 집의 정상 지상 외벽에 접함.
- 여러 집에 닿지 않고 건물·도로·오브젝트와 겹치지 않으며 입구가 막히지 않음.

큰 영역·비정형·분리된 영역은 일반 지상 주차 계산을 따른다.
채택된 차고는 주차 입력이 소유하며 집의 Grid를 변경하지 않는다. 공유하는 집 벽은 솔리드 모듈로 바꾸고,
그 자리에 차고 벽을 중복 생성하지 않는다. 주차 영역을 제거하면 집 벽을 복원한다.
도로를 향한 차고 문도 실제 차량 진입 검증은 `not-verified`이며 지상 검증 주차 대수에 합산하지 않는다.

구현: [residential-kit.ts](../src/core/residential-kit.ts), [attached-garages.ts](../src/core/attached-garages.ts).
기존 사례: [residential.test.ts](../tests/residential.test.ts), [attached-garages.test.ts](../tests/attached-garages.test.ts).

## 13. 편집 결과와 실패를 다루는 공통 룰

부피·도로·인도·주차·오브젝트가 바뀌면 전체 규칙을 재평가한다.
높이 변경은 수직 구간 전체에, 도로 단절은 멀리 있는 입구·시설·주차 접근에 영향을 줄 수 있다.
같은 완전한 입력은 같은 결과를 낸다. 여기에는 seed·컨셉·anchor·명시 설정도 포함된다.
성분 분리/병합은 보존 규칙에 따라 anchor를 상속하며 최종 셀만 같다고 동일 입력으로 보지는 않는다.

공간 부족·지지 상실·접근 실패·선택 마감 탈락은 해당 결과와 진단에 표현하고 가능한 나머지를 유지한다.
잘못된 저장 형식·필수 면 소유 중복·등록 bounds 이탈 같은 계약 오류는 마지막 수락 문서와 화면을 유지한다.
외피의 구조면은 정확히 한 결과가 소유해야 하며, 창·문·난간을 그릴 때 중복 면으로 덮지 않는다.
카메라·표시 지면·분석 레이어는 생성 입력을 바꾸지 않는다.

개발 중 기대한 결과가 없으면 Inspector에서 원본 입력, 실제 지지면, 선택/탈락 후보,
`reasonCodes`, 충돌 예약, 접근 상태를 먼저 확인한다. 그림이 존재하는 것과 이동이 검증된 것을 구분한다.
현재 지원 범위에는 실내 이동·시설 수직 이동·상층 주차 연결·지형/물·구조 하중 해석이 포함되지 않는다.

구현: [environment-generation.ts](../src/core/environment-generation.ts), [environment-editor.ts](../src/environment-editor.ts).

## 룰을 수정할 때

1. 위 동작에서 바뀌는 입력 조건·결과·예외를 먼저 명확히 하고 해당 core 파일을 수정한다.
2. 관련 기존 테스트에서 조건 경계와 실패 사례를 확인한다. 예를 들어 교통섬은 폭 3/4와 면적 24/25,
   입구는 발판 유무와 도로 접근/로컬 접근, 외벽은 낮은 높이·단차·반복 쌍 경계를 다룬다.
3. 공유 계산 룰이 바뀌면 프로젝트 디렉터리에서 `npm run verify`를 수행한다.
   편집/표시 동작이 바뀔 때만 관련 브라우저 사례를 추가로 확인한다.
4. 동작 설명은 이 가이드, 정확한 수식·계약은 [생성 규칙 명세](GENERATION_RULES.md)에 함께 반영한다.
   보존 baseline을 변경 후 결과로 덮어써 차이를 숨기지 않는다.
