# 큰 건물의 실제 편집 지연 측정

`e2e/building-edit-measure.spec.ts`는 부피 파일을 실제 편집기에 읽힌 뒤 마우스로 옥상 전체를 선택하고, 실제 E/Q 키와 정사각뿔 핸들 드래그로 층을 편집한다. 규칙 함수를 직접 호출한 시간과 화면에 반영되는 시간은 구분한다.

## 재현 조건

- 입력: Seed 42, X×Y×Z = 28×24×28, 옥상 선택 784칸. A(`shop`)와 C(`urban-shop`).
- 성분 하나인 꽉 찬 부피이며 도로·주차·시설물 원본 입력은 없다. 외피·공간 예약·접근·충돌 검증은 일반 편집 경로 그대로 실행한다. 주차 경로 탐색 같은 입력이 없는 계획의 비용을 이 수치로 일반화하지 않는다.
- 브라우저: Playwright Chromium, headless, 1440×960. 정확한 브라우저 버전·CPU·WebGL renderer·빌드 SHA256은 JSON에 기록한다.
- 최초 추가/제거: 매번 새 브라우저 context에서 처음 읽은 장면을 선택한 후 E 또는 Q. 각각 10개 표본. 초기 장면 표시를 위해 생성된 geometry/계획 캐시는 이미 존재하므로, 이것은 **최초 편집**이며 캐시가 없는 최초 장면 생성과 다르다.
- 별도 최초 장면: `building-startup-measure.spec.ts`에서 스타일당 새 context 3개. 기존 `environmentMeasure.accept`의 계측을 재사용하며 시작시 계획/geometry 캐시 0, 자동 startup 생성 0을 확인한다. 이후 두 번의 rAF까지 기회 구간도 기록한다. 최초 편집 결과와 섞지 않는다.
- 반복 키: E/Q 준비 4회 뒤 E/Q 30회. 높이 24와 25를 왕복한다.
- 연속 드래그: 마우스를 누른 채 +1/+2/+3층을 거쳐 원래 높이까지 되돌리는 한 제스처를 5회 수행한다. 총 30개 채택 편집이며 각 층에 같은 공간 검증·생성·이력 경로를 적용한다.
- 초기 장면·카메라·표시 레이어·seed·입력·측정 구간을 전후 동일하게 유지한다. 다른 브라우저 회귀·코어 벤치마크와 겹치지 않게 실행한다. 입력은 Playwright가 브라우저 처리 속도에 맞춰 연속 전송하며 고정 120Hz 입력 폭주 시험은 아니다.

Windows PowerShell 재현:

```powershell
npm run build
$env:BUILDING_MEASURE_OUTPUT='benchmarks/building-edit.after.json'
npx playwright test --config playwright.building-measure.config.ts building-edit-measure.spec.ts
$env:BUILDING_STARTUP_OUTPUT='benchmarks/building-startup.after.json'
npx playwright test --config playwright.building-measure.config.ts building-startup-measure.spec.ts
```

변경 전 진단 빌드에는 CPU profile의 원본 함수 매핑을 위한 source map/comment만 추가했고, 최종 변경 후 빌드는 일반 production 빌드를 사용했다. 번들 최적화 설정은 동일하며 실제 JS/CSS SHA256은 각 보고서에 남긴다.

비교 기준은 원본 HEAD `0254855`의 별도 checkout에 **같은 측정 코드만** 적용한다. `before.json`과 `after.json`은 모든 원시 표본을 보존한다. `BUILDING_MEASURE_PILOT=1`은 작은 표본 진단과 CDP CPU profile 수집에만 사용하며 최종 비교에는 사용하지 않는다.

임시 checkout 없이 기준을 재현하려면 원본 커밋을 별도 작업 디렉터리에 준비한 뒤 저장소 루트에서 [측정 전용 패치](../benchmarks/building-baseline-instrumentation.patch)를 `git apply`로 적용한다. 패치는 `main.ts`, `measurement.ts`, `viewer.ts`, `crafted-geometry.ts`의 계측만 포함하며 `src/core` 변경은 없다. 현재 작업의 `e2e/building-edit-measure.spec.ts`, `e2e/building-startup-measure.spec.ts`, `playwright.building-measure.config.ts`를 해당 프로젝트의 같은 위치에 복사하고 같은 의존성 버전으로 위 명령을 실행한다. 패치의 읽기 전용 `timings` getter는 별도 최초 장면 측정 전에 추가되었으며 기본 편집의 측정 구간에서는 호출하지 않는다.

## 시간의 의미

| 필드 | 범위 |
| --- | --- |
| `inputQueueMs` | native event의 timestamp부터 document capture listener 실행까지 |
| `synchronousMs` | native event부터 문서·생성·Viewer 동기화·이력·UI 채택 완료까지 |
| `handlerToSync` | 위 동기 채택 시간에서 입력 대기를 뺀 값 |
| `inputToRenderMs` | native event부터 새 결과를 포함하는 다음 WebGL render 호출의 CPU 반환까지 |
| `generation` | 기존 생성 stageHook 전체; Viewer 제외 |
| `generationOther` | 생성 전체에서 공개 stageHook 구간 합을 제외한 시간. 문서 검증/직렬화/캐시 작업 및 기타 생성 조립 포함 |
| `steps` | 표면 편집, 문서 교체, 동일 문서 비교, UI publication, 이력 직렬화 |
| `rendererStages` | clear, 부피/선택 갱신, 환경 오버레이, scene Mesh, 면 Mesh, 분석 Mesh. `geometryBuild`는 면 Mesh 구간에 포함되는 cache miss 하위 구간 |
| `renderSubmissionMs` | 새 결과를 그리는 WebGL render 호출의 CPU 시간 |

`generationOther`는 직렬화만을 순수하게 분리한 값이 아니다. CPU profiler의 별도 진단으로 연결 성분 분석·정규화·복제·직렬화·불변화·메모리 회수 위치를 확인한다. 모든 native event가 별도 화면으로 나타나는 것은 아니다. 같은 프레임 전에 여러 드래그 층이 채택된 경우 `supersededBeforeRender`로 표시한다. 표본 버퍼는 측정 모드에서만 만들며 최근 256개로 제한한다.

## 진단 및 제한

수정 전 28×24×28 A의 반복 편집 4회를 별도 CDP profile로 확인했다. 애플리케이션 self-time 상위 항목은 `buildingComponents`, `analyzeVolume`, cell ID/인접 좌표 구성, canonical JSON·불변화였다. 실제 수직 구간 계산은 개별 편집 약 2–4ms로 작았으며, 별도 파일로 기록한 반복 편집 pilot에서는 새 geometry 빌드가 0ms였다. 최초 편집은 새 에셋 키가 필요할 수 있으므로 최종 표본의 `geometryBuild`를 따로 기록한다. 프로파일은 병목 위치를 찾기 위한 별도 실행이며 전후 지연 표본에 합산하지 않는다.

여기서 편집의 화면 반영 지연은 **CPU render submission까지**다. 별도 최초 장면은 기존 accept 종료 후 두 번의 rAF까지 구간으로, 화면을 그릴 기회가 지난 것을 확인한다. GPU 완료, compositor의 실제 paint, 모니터 표시 지연은 측정하지 않는다. 실제 backend는 ANGLE Vulkan의 **SwiftShader**였으므로 사용자의 하드웨어 GPU 지연으로 일반화할 수 없다. p50/p95/최댓값과 표본 수를 함께 읽어야 하며 최초 편집 n=10과 최초 장면 n=3의 p95는 최댓값이므로 안정적인 극단 지연 추정으로 해석하지 않는다. 최초 장면은 navigation을 제외하고 하나의 Chromium 프로세스 안에서 새 context를 사용하며 OS/프로세스 전체를 재시작한 cold boot가 아니다.

최초 geometry 자체의 개선은 확인되지 않았다. 특히 C의 geometry 구축 중앙값은 5.8→7.3ms로 늘었으며 n=3으로 원인을 일반화하지 않는다. 최초 수락 전체는 A 316.7→274.1ms, C 346.1→295.0ms로 감소했다. 최초 장면의 입력/출력 signature도 변경 전후 동일하다.

## 남은 히치와 검증 범위

연속 드래그의 handler 중앙값은 A 404.8→289.9ms(28.4% 감소), C 417.6→281.8ms(32.5% 감소)다. 같은 입력의 화면 제출 중앙값은 A 801.3→698.8ms, C 745.4→591.0ms이며 p95는 각각 854.0→763.3ms, 811.9→677.8ms다. **히치는 줄었지만 사라지지 않았다.**

외피/영역 분석, 문서 변환 및 생성의 미분리 구간은 계속 비용을 차지한다. A/C 드래그 입력 대기 중앙값은 360.2/279.5ms, 렌더 호출 CPU 중앙값은 30.2/28.8ms다. SwiftShader 입력 대기가 남아 전체 화면 제출 개선율이 CPU 수락 개선율보다 작다. 큐 대기의 내부 GPU/드라이버 원인을 별도로 추적하지 않았으며 하드웨어 GPU의 실제 paint 개선을 주장하지 않는다.

모든 세부 꼬리 지연이 개선된 것은 아니다. A 반복 입면 p95는 52.0→71.6ms, C 반복 preflight 최댓값은 35.9→92.6ms, C 반복 렌더 CPU 최댓값은 33.8→66.2ms였다. 이 스파이크의 GC/드라이버 원인을 별도 계측하지 않았다. 입력부터 제출까지의 전체 p95/최댓값은 여덟 분포 모두 감소했지만, 이를 모든 하위 비용의 개선으로 확대하지 않는다.

측정은 전후 모두 통과했다. 각 키 편집은 채택 표본 하나, 각 held drag는 3층 추가/3층 제거의 채택 표본 여섯 개와 원래 셀 수 복귀를 확인한다. 변경 후 표본에서 render 전에 대체된 중간 상태는 0개다. 결과의 의미/geometry/실제 이미지·Undo/Redo·저장 복원과 전체 재생성 동등성은 [별도 보존 보고서](BUILDING_REFACTOR_PRESERVATION.md)에 있다.
