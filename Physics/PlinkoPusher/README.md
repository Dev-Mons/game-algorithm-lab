# Plinko Pusher Lab

Unreal Engine에 적용하기 전에 **플링코(주 가공) → 코인푸셔(부산물 보너스)** 장치의 공간 구성, 가공 흐름, 게임적인 물리 감각과 성능을 웹 3D로 검증하는 독립 실험 프로젝트입니다. 자체 간이 물리(Custom)와 기존 물리엔진(Rapier)을 같은 인터페이스 뒤에서 교체·비교할 수 있습니다.

전투·성장 트리·서버·로그인·배포·Unreal 프로젝트는 범위 밖입니다. 외부 에셋 없이 기본 메시만 사용합니다.

## 실행

Node.js 22 이상. 이 폴더(`Physics/PlinkoPusher`)에서 실행합니다.

```powershell
npm ci
npm run dev        # http://127.0.0.1:4190/
```

Windows에서는 `run.bat`도 됩니다.

| 명령 | 내용 |
| --- | --- |
| `npm run verify` | 타입 검사 + 단위 테스트 + 빌드 |
| `npm run test:e2e` | 헤드리스 Chromium(새 헤드리스, 가능하면 하드웨어 GPU) 브라우저 테스트. 창을 띄우지 않음 |
| `npm run measure` | 렌더링 없는 Node 물리 비교(프리셋 × 백엔드 조합 × 3회). `artifacts/measurements.json` |
| `npm run measure:browser` | 렌더링 포함 브라우저 순차 비교. UI의 측정 실행 → A/B 저장 흐름을 헤드리스로 구동. `artifacts/browser-measurements.json` |

URL 예: `/?preset=stress&plinko=rapier2d&pusher=rapier3d-planar&placement=compound&camera=pusher&paused=1&seed=7&quality=low&seedTokens=150` (`seedTokens`: 초기 적재 토큰 수)

## 화면과 조작

- 기본 화면은 장치 중심으로 표시합니다. 하단 **실험 설정** / **생산 · 검증** 버튼으로 기존 패널과 순차 비교를 열 수 있습니다. 라벨은 기본 꺼짐입니다.
- 오른쪽: 폭 약 2.73의 **한 칸 저장통**(이전 폭 8.2의 1/3). 가운데 세로 분할대를 없애고, 앞뒤 한 겹만 들어가는 얕은 깊이를 유지합니다. 원재료가 2D 중력·원형 충돌·경사 바닥을 따라 내려와 쌓이고, 하단 게이트에 도착한 재료만 내부 이송으로 넘깁니다. 실제 대기 재료를 표시하며 **저장통 +100**으로 채울 수 있습니다. 저장통 하부의 구동부 → 밀폐된 하부 벨트·후면 상승 이송 → 보드 전체 폭의 분배 호퍼로 연결됩니다. 내부 이송체는 외장 안에 가려지고 투입구에서 모습을 드러냅니다.
- 뒤쪽 위: 로컬 28×10 플링코 보드는 **균일 0.8 배율**(표시 22.4×8)로 표시합니다. 압축부를 왼쪽으로 분리하면서 플링코와 푸셔의 작업 폭을 함께 넓혔습니다. 로컬 물리 치수·점수 공식은 유지하며 보드·페그·호퍼·연결부를 같은 BoardFrame에서 도출합니다. 보드는 바닥과 **50° 경사**, 수직 기준 뒤로 40°입니다. 12개 투입구가 양 끝까지 분포하며, 재료는 각 개구부를 통과한 동일 위치·속도로 보드 물리에 인계됩니다. 9행×21열 지그재그 페그와 볼트 프레임, 황색 안전 도장, 금속 패널, 따뜻한 작업등을 사용합니다.
- 왼쪽: 플링코 하단 **8칸 수용부** → 얕은 수집 통로 → **가려진 부산물 이송부** → 측면 케이스 안 리프트 → **부산물 더미 관찰창**으로 이어집니다. 크기·방향이 다른 납작한 금속 잔해가 중앙 입구에서 떨어져 2D 중력·충돌로 얕은 받침에 쌓입니다. 한 묶음이 모이면 상부 유입을 닫고 **보이는 누름판이 한 번 내려옵니다**. 조각을 찌그러뜨리지 않고 받침과 더미를 함께 내려 **하부 가림판 뒤로 밀어 넣습니다**. 모든 조각이 가려진 처리부에 들어간 뒤 동일 개수의 코인을 왼쪽의 2열×4레인 포켓에서 꺼내 밀폐된 분배부 안에서 **4개 수직 출구**로 전달합니다. 가운데를 지나가는 부산물·코인과 벨트 운동은 표시하지 않으며 출구 입구부터 코인이 보입니다. 출구는 왕복 푸셔 판의 중앙 위에 있습니다. 왼쪽 본 재화 슈트·수거함은 없으며 본 재화 지급 공식은 유지합니다.
- 앞쪽 아래: 기본 트레이의 작업 폭은 플링코 표시 폭과 같은 **22.4**이며, 왕복 판·가드·충돌 경계·보상 가장자리·수거함이 같은 폭 설정을 사용합니다. 깊이와 코인 크기는 유지합니다. 뒤쪽 왕복 푸셔(윗면 선반 + 고정 립)가 여러 층 더미를 밀면 가장자리 너머로 무너져 보너스 수거함에 떨어집니다. 스트레스 프리셋의 별도 22×16 트레이는 유지합니다.
- 원석은 회갈색 저다면체이며 가공 점수가 오르면 녹색을 띱니다. 부산물은 크기가 다른 회색·갈색의 납작한 금속 파편이고, 생산 코인은 가치 1의 각인된 금속 원판입니다. 부산물 가치 1이 실제 코인 1개가 됩니다. 초기 적재 토큰은 탁한 회색이며 기존 가치 8을 유지합니다.
- 호퍼/압축/투입/수거 라벨과 수치는 선택적으로 켤 수 있습니다. 기본 화면은 화살표 없이 입출구·통로·이동으로 공정을 표시합니다. 전체 카메라는 25° 시야각으로 원근을 줄여 플링코가 멀리 작게 보이는 현상을 줄이고 왼쪽 압축탑·오른쪽 저장통까지 함께 맞춥니다. 연결부 카메라는 왼쪽 프레스와 벨트 연결을 근접 표시합니다. 페그 접촉 링, 압력 표시등, 왼쪽 다이의 배출 셔터, 네 출구의 셔터, 가장자리 작업등이 상태를 보여 줍니다.

| 영역 | 조작 |
| --- | --- |
| 실행 | 프리셋(구조 확인 / 기본 가동 / 원재료 과잉 / 부산물 과잉 / 성장 후 / 스트레스 / 빈 상태), 자동 데모, 일시정지, 초기화, 배속(0.25–4×), 시드 |
| 투입 | 원재료 +1, 묶음 +10, 저장통 +100, 자동 공급 |
| 물리 백엔드 | 플링코: Custom 2D / Rapier 2D. 푸셔: **Rapier 3D 적층**(기본) / Custom 적층 2.5D / Custom 단층(참고) / Rapier 3D 평면 제약. 변경하면 현재 실험을 종료하고 같은 초기 상태로 재시작 |
| 화면 밖 처리 | 처리량 근사 모델로 전환(아래 참고) |
| 보드 배치 | 와이드 기본(바닥과 50°) / Y축 35° / X축 −25° / 법선축 12° / 부모+복합. 실행 중 바로 적용(로컬 물리 상태 유지) |
| 카메라 | 전체 / 플링코 / 푸셔 / 연결부 / 측면 / 후면 / 초기화. 드래그 360° 회전·휠 확대, 거리 제한 |
| 설정 | 공급량, 플링코 처리량, 페그 레벨, 페그 종류 배치, 본 가치, 부산물 계수, 한 번에 압축할 개수(1–24), 푸셔 왕복 주기(속도)·스트로크(공급 위치 재배치를 위해 재시작), 트레이 토큰 상한·초기 적재 토큰(재시작), 품질 |
| 페그 | 클릭(드래그 아님)해 선택 → 종류·레벨 개별 변경. 개별 설정은 초기화·백엔드 교체·측정 반복에 유지되며, 프리셋 또는 전체 페그 패턴·레벨 변경 시 초기화 |

오른쪽 패널은 원재료 저장·내부 이송·보드 처리 중·완료, 본 재화, 부산물 대기(슈트·압축 버퍼·배출 대기), 트레이 잔존 가치, 낙하 수량, 보너스(생산/초기 적재 분리), 합계, 최근 처리량, 검증 지표(가치 보존 오차, 중복 무시, 유실 복구, 활성 월드 수)와 성능 통계를 표시합니다.

## 공정과 경제 규칙

```
원재료 공급 → 오른쪽 저장통 → 내부 벨트·리프트 → 전체 폭 분배 호퍼 → 투입구 → 플링코 낙하·페그 접촉 → 하단 처리기
  ├ 본 재화 즉시 1회 지급
  └ 8칸 수용부 → 밀폐 부산물 이송 → 왼쪽 리프트 → 부산물 물리 누적 → 누름판·받침 하강 → 가려진 처리부 → 밀폐 코인 분배 → 4개 수직 출구 → 푸셔 판 상판 → 트레이 → 푸셔 → 보상 가장자리 낙하 → 보너스 1회 지급
```

기본 보드는 와이드 배치를 위해 치수와 페그 행·열, 공급 위치가 바뀌었습니다. 접촉 궤적과 평균 산출량은 이전 배치와 달라질 수 있지만 아래 점수·상한·지급 공식과 부산물 가치 1당 코인 1개 규칙은 같습니다.

모든 가치는 정수이고 설정은 `src/core/config.ts`에 있습니다. 명칭(원재료/가공 재화/부산물 토큰/회수 보너스)과 수치는 임시입니다.

| 항목 | 공식 (기본값) |
| --- | --- |
| 페그 점수 | 원재료마다 **처음 접촉한 페그만** 점수. 서로 다른 페그 `maxScoredHits`(24)개까지. 점수 = 종류 기준 × 레벨(1–5). 기본(가공1·부산물1), 정련(가공3·부산물0), 분리(가공0·부산물3) |
| 본 재화 | `mainBase(10) + floor(mainPerProcess(1) × min(가공 점수, processCap(60)))` |
| 부산물 가치 | `min(byproductCap(40), byproductBase(2) + floor(byproductCoef(1) × 부산물 점수))` |
| 토큰화 | 재료가 모이면 한 번에 최대 `tokenBundleMax(12)`조각을 고정해 0.4s 동안 함께 압축하고 **동일 개수의 가치 1 코인**을 만든다. 최대 24개/회. `tokenValue(8)`는 기존 초기 적재 가치만 유지한다 |
| 회수 보너스 | `floor(토큰 가치 × bonusRate(1))` |

지켜지는 규칙과 근거(테스트: `tests/unit/economy.test.ts`):

- 8칸 수용부 하단 도착 즉시 본 재화를 한 번 지급합니다. 슈트는 용량 제한이 없는 논리 대기열이라 압축기·트레이 적체가 본 재화 지급을 막지 않습니다.
- 부산물 생성·압축·트레이 도착으로는 보너스가 없습니다. 물리 백엔드가 **보상 가장자리를 넘어 낙하가 확정된 사실**을 보고하면 `GameCore`가 트레이 기록에서 토큰을 지우며 한 번 지급합니다. 같은 토큰의 반복 보고·낙하 연출·메시 제거는 지급과 무관합니다(중복은 `duplicateExits`로 셈).
- 공급 > 처리량이면 원재료 대기가, 부산물 공급 > 압축·회수량이면 더미와 유입 대기가 증가합니다. 관찰창에는 현재 묶음(기본 12개, 최대 24개)을 받고 추가 재고는 연결된 상부 유입에 대기시킵니다. 묶음이 모이거나 소량 대기 시간이 지나면 유입을 닫고 조각이 안착할 때까지 기다립니다. 최소 적재·누름판 전진 0.3s → 가압 0.4s(앞 20% 더미까지 빠른 접근, 다음 60% 더미·받침 동반 하강, 마지막 20% 유지) → 복귀 0.2s → 내부 분배 4s와 판 위치에 따른 게이트 대기 → 출구별 수직 낙하 → 마지막 그룹 배출 후 0.35s 순서입니다. 누름판은 유입 중 뒤로 물러나 입구를 비웁니다. 조각의 반지름·방향·상대 배치는 하강 중 유지하며 전부 가림판 아래로 들어가야 코인 생성이 허용됩니다. 묶음 크기 설정 변경은 다음 빈 받침의 적재부터 적용됩니다.
- 압축된 코인은 왼쪽 다이의 고정 포켓(2열×4레인·최대 3층)에 남습니다. 기본 12개, 설정 시 최대 **24개**를 함께 만듭니다. 내부 분배 경로는 외장 안에 가려집니다. 출구의 마지막 구간에서 수직으로 내려온 위치·속도를 그대로 강체 물리에 인계하며 앞으로 던지는 속도는 0입니다. 기본 적층 모드는 전진한 푸셔 판 중앙에 해당하는 고정 투입점으로 떨어뜨립니다. 낙하 시간·코인 층 높이·왕복 주기를 계산해 착지할 때 판이 아래에 오는 구간에만 출구를 엽니다. 판에 올라간 코인은 고정 립에 의해 트레이로 내려와 다음 전진에 밀립니다. 반지름·두께를 고려한 통로 폭·벽 여유를 공통 배치에서 계산합니다.
- 출구는 최소 **0.1초 간격**으로 열립니다. 푸셔 판이 착지를 받을 수 없는 시점에는 코인을 밀폐된 출구 안에서 기다리게 합니다. 한 출구가 높은 더미에 막히면 해당 그룹은 연결 통로의 현재 위치에서 기다리고, 다른 출구는 이동 경로가 비어 있으면 진행할 수 있습니다. 앞쪽으로 방향을 바꾸는 구간에서 대기 중인 다른 묶음과 겹칠 경우에도 정지하므로 출구 완료 순서는 적체에 따라 달라질 수 있습니다. 새 압축은 현재 묶음의 모든 그룹을 배출한 뒤 시작합니다. 토큰 ID별 포켓 위치를 유지해 먼저 배출된 그룹 때문에 나머지가 옆자리로 이동하지 않습니다. 트레이 상한·출구 반지름 여유를 검사하며 더미 높이에 맞춰 생성 위치를 바꾸지 않습니다.
- 단층 비교 모드는 수직 물리가 없어 기존 판 앞쪽의 별도 고정 투입점에 가이드로 코인을 한 층 내려놓습니다. 하강·복귀 시간과 푸셔 위치·평면 점유를 검사합니다. 좁은 빈자리·짧은 스트로크에서는 공급이 제한될 수 있습니다. 적층 모드도 고정 립 앞에 코인이 올라갈 상판 공간이 없는 스트로크에서는 공급을 보류합니다.
- 화면 안 부산물 이송은 기존 처리 시간 1.2s에 벨트·리프트 3.2s를 더한 총 4.4s를 사용합니다. 도착 전의 수량은 GameCore의 슈트에 남고, 도착 후에만 왼쪽 압축 버퍼로 이동합니다. 본 재화는 보드 하단 도착 시 즉시 지급되며 이송 시간으로 보상을 추가하거나 차감하지 않습니다. 화면 밖 처리는 기존 처리량 근사 시간 모델을 유지합니다.
- `src/lab/device-layout.ts`가 8칸 수용부, 회전 보드와 연결되는 수집 통로, 왼쪽 압축실, 두 벨트와 4개 출구의 이동 경로를 공유합니다. `PlinkoBoardSpec.receiving`은 두 플링코 백엔드의 칸막이 충돌에 쓰며, 도착 이벤트는 최종 로컬 위치·속도를 함께 전달합니다. 연출→물리 전환은 `Simulation`의 고정 스텝에서 결정하며 화면 갱신 주기에 의존하지 않습니다. 보상 이탈 연출도 마지막 위치·속도·회전을 이어 받습니다.
- 본 재화와 보너스는 같은 임시 재화 합계로 더하되 출처(가공/생산 보너스/초기 적재 보너스)를 따로 표시합니다. 초기 적재 토큰은 생산 부산물과 별도 기록합니다.
- 가치 보존식(`conservationError`)이 항상 0입니다: 생성 부산물 = 슈트 + 압축 버퍼 + 배출 대기 + 트레이 + 화면 밖 트레이 풀 + 지급 완료. 비정상 유실 원석은 대기열로, 유실 토큰은 투입 대기로 되돌려 가치를 버리지 않습니다. 단층 조건에서 한 층에 들어가지 않는 초기 적재 토큰도 투입 대기로 보냅니다.
- 표시 제한(원재료 저장통 최대 720개, 부산물 묶음 최대 24개, 낙하 연출 96개)은 수량·가치를 삭제하지 않습니다. 부산물 받침이 가득 차면 추가 재고는 연결된 상부 유입 대기로 보존하며 빈자리에만 입자를 투입합니다.
- 베팅·꽝·원금 손실 규칙은 없습니다.

## 보드 로컬 좌표 계약

플링코 원석의 이동·충돌은 보드 로컬 2D에서만 계산합니다. 보드가 월드 X/Y 평면에 있다고 가정하지 않습니다(`src/core/frame.ts`).

- 로컬 좌표 `(u, v)`: 원점은 보드 왼쪽 위 모서리, `u` 오른쪽, `v` 아래쪽. 로컬 중력은 기본적으로 `+v`(장치 내부 게임 중력, 보드를 돌려도 불변).
- 기저: `uAxis`, `vAxis`, `normal`은 서로 직교하는 단위 벡터입니다. `v`가 아래쪽이므로 `u × v = −n`입니다.
- 변환: `world = origin + (uAxis·u + vAxis·v + normal·depth) × scale`. 역변환은 각 축과의 내적 / scale.
- `src/core/raw-feed.ts`의 실제 투입구 중심을 순회합니다. `GameCore.rawTransit`이 저장통에서 예약한 ID와 이송 시간을 보존하며, 보드 동시 수용량에는 내부 이송도 포함합니다. 게이트를 열어 실제 2D 원재료가 하단 공급 포켓까지 통과한 후에만 수량을 차감합니다. 이때 마지막 물리 위치를 내부 이송 경로의 시작점으로 인계합니다. 원재료 보존식은 `공급 = 저장 + 내부 이송 + 보드 + 처리 완료`입니다.
- 내부 이송 시간은 보드 배치와 무관하게 동일합니다. `rawFeedRoute`가 밀폐된 이동 경로를 공유하고, 마지막 가시 구간은 일정한 로컬 속도 2.2로 내려옵니다. 마지막 표시 위치 `v=-1.65`, `vu=0`, `vv=2.2`를 물리 백엔드에 그대로 인계해 열린 상단 `v=0`을 통과합니다. 투입 위치를 무작위로 생성하지 않습니다.
- `depth`는 원석을 보드 면에서 띄우는 시각 오프셋(0.3)이며 충돌에 쓰지 않습니다.
- 보드 Transform = 부모 Transform ∘ 자식 Transform(`composeTransforms`). 표시 그룹도 같은 Transform을 쓰며, 원석 월드 위치는 코어 `localToWorld`로 계산합니다(두 경로 차이는 테스트에서 1e-5 미만).
- **비균일 스케일은 차단**합니다(`uniformScale`이 예외). 논리 형상은 `BoardDims`, 표시 축소는 균일 `BoardFrame.scale`로 바꾸며 이번 축소에서는 로컬 물리 치수를 유지합니다.
- 페그 선택: 화면 → 카메라 광선 → `rayToLocal`(보드 면 교차) → 로컬 `(u, v)` → `pickPeg`(정적 격자 인덱스). Three.js 좌표·카메라는 코어에 들어가지 않습니다.
- 월드 중력 투영(`gravityMode: 'world-projected'`)은 별도 옵션입니다. 이 모드에서는 배치 변경 시 재시작합니다. 기본 모드와 섞지 않습니다.
- 원석 회전은 표시용이며 경제 판정·2D 궤적에 영향이 없습니다. 움직이는 보드의 관성은 구현하지 않습니다.

검증: 5개 배치 모두 기저 직교·왕복 변환·광선 페그 선택이 일치하고(`tests/unit/frame.test.ts`), 배치만 다른 실행에서 Custom·Rapier 모두 로컬 궤적·수익이 **완전히 동일**합니다(`tests/unit/physics.test.ts`). 브라우저에서 5개 배치를 실제 화면으로 띄워 페그 화면 위치를 클릭해 같은 페그가 선택되는지 확인합니다(`tests/browser/lab.spec.ts`).

코어와 렌더러는 엔진의 World·Body·Collider를 참조하지 않습니다. 엔진 접촉 콜백은 어댑터 안에서 `PlinkoEvent`로 정규화합니다. 백엔드는 영역을 벗어난 물체를 스스로 제거하고 한 번만 보고하며, 이후 `remove()`는 무시합니다. `liveBackends` 계수로 교체 후 이전 월드가 남지 않는지 검사합니다.

### 고정 스텝 파이프라인(틱 1회, 60 Hz)

시간·공급 → 저장통 예약·내부 이송 완료 → 호퍼 입구에서 물리 원석 인계 → 플링코·8칸 수용부 step → 도착 사실 정산 → 공통 푸셔 운동 → 출구 여유 검사·연결 통로 이송·물리 인계 → 푸셔 step → 이탈 정산 → 부산물 누적·가압·복귀.

투입구 게이트는 배출 준비 상태에서 현재 푸셔 상태를 전용 버퍼로 읽습니다. `sync()`는 표시·측정용 스냅숏만 갱신하므로, 매 틱 호출하든 여러 틱마다 호출하든 같은 고정 스텝 입력의 물리·정산 결과가 같습니다. 판정용 상태 조회 비용은 `coreStep`, 표시용 조회 비용은 `transfer`에 포함됩니다.

렌더링과 분리되어 있습니다. 한 프레임에 최대 6스텝만 따라잡고 남은 시간은 **버립니다**(시뮬레이션이 느려지며 `버린 시간`에 기록). 큰 dt를 물리에 넘기지 않습니다. 렌더 보간은 하지 않습니다.

## 물리 백엔드

### Custom

- 푸셔 **적층 2.5D**(`pusher-custom-stack.ts`, 대량 토큰 후보): 토큰은 회전 동역학 없는 수평 원판 `(x, y, z)`입니다. 고정 스텝마다
  1. 중력 적분, 받침이 있을 때만 쿨롱 마찰 감속, 푸셔 판 윗면에 얹힌 토큰은 판 속도로 이동
  2. 6회 반복: 바닥(중심이 가장자리 안쪽일 때만, 하중이 있으면 반지름 × `overhang`(0.5)까지 돌출 허용), 판 앞면(전진 시 고정 물체 취급)·판 윗면, 고정 립, 측면 가드, 원판 쌍 분리(수평·수직 중 얕은 축. 수직이면 위 토큰만 들어 올리고 받침으로 기록)
  3. 위치 변화로 속도 갱신(얹힐 때 반발 0), **받침 밖 무게중심 미끄러짐**(받침 1개면 0.3r, 2개 0.45r, 3개 이상 0.6r을 넘으면 바깥으로 가속)
  4. **경사 붕괴**: 반지름 크기 높이 격자에서 이웃 칸보다 반지름 × `reposeSlope`(0.9) 이상 높은 꼭대기 토큰을 낮은 쪽으로 미끄러뜨림(휴면 토큰도 검사해 깨움)
  5. **마찰 결합**: 정지한 토큰 위 토큰은 받침의 수평 속도를 `coupling`(0.9) 비율로 따라감 → 밀린 더미가 덩어리로 움직임. 미끄러지는 중인 토큰은 운동 마찰 0.1만 받음(강한 결합을 걸면 무너짐 속도가 매 스텝 지워져 더미가 공중에 솟은 채 버티는 문제가 있었음)
  6. 받침이 제거된(낙하한) 토큰 위의 휴면 토큰을 깨워 연쇄 붕괴, 바닥 아래로 떨어지면 이탈 확정
  - 기울기는 받침 위치로 추정한 표시용 값이며 충돌 형상은 항상 수평 원판입니다. xz 균일 격자 + 고정 반복으로 전 쌍 비교·무제한 반복이 없습니다.
  - `reposeSlope`·`coupling`·`overhang`은 경험적 계수입니다. 현재 값에서 공중 더미는 없지만 Rapier만큼 큰 붕괴는 나오지 않습니다(아래 감각 측정).
- 푸셔 단층(`pusher-custom.ts`, 참고용): 위치 기반 단층 원판. 쌓임이 없어 코인푸셔의 핵심 감각을 만들지 못하므로 단층 비교 기준으로만 남깁니다.
- 플링코: 중력 → 선형 감쇠 → 속도 상한 → 이동 → 원끼리(동적 균일 격자) → 페그(정적 균일 격자) → 벽, 틱당 4 서브스텝. 반발·접선 마찰 임펄스. 끼임 보정: 1.2초 동안 0.35/s 미만이면 좌우 교대로 3/s 밀기.
- 단층 푸셔 세부: 쿨롱 마찰 감속 → 이동 → 6회 반복(판 앞면, 격자 이웃 쌍, 측면 가드) → 위치 변화로 속도. 해소되지 못한 겹침은 시각적 포개짐으로만 표시하며 실제 적층이 아닙니다.
- 두 Custom 푸셔 모두 전진하는 판에 닿은 원판을 그 스텝의 고정 물체로 취급해 밀림을 전달하고, 후퇴하는 판은 끌어당기지 않습니다(테스트). 반복당 보정 거리 반지름 × 0.5, 속도 상한 6/s, 휴면 0.04/s 미만 0.4초.

### Engine: Rapier (`@dimforge/rapier2d-compat`, `@dimforge/rapier3d-compat` 0.21)

선정 근거: Apache-2.0, 공식 JS/WASM 배포(compat 패키지는 WASM 내장으로 Vite·Node 모두 별도 설정 없이 동작), 같은 계열의 네이티브 2D·3D 엔진 제공(플링코에 3D 평면 제약을 쓸 필요가 없음), 휴면·충돌 그룹·키네마틱 바디·고정 스텝 제어, step 단위 계측 가능. 처음부터 여러 엔진 후보를 연결하지 않았습니다.

- 플링코 `rapier2d`: 로컬 `(u, v)` = Rapier `(x, y)`, 중력 `(0, +g)`. 공 대 페그 접촉 시작 이벤트를 페그 접촉 사실로 정규화. 도착 기준(`v ≥ height`)·속도 상한·끼임 보정은 Custom과 같은 공통 규칙. 틱당 1 step, solver 반복 4, CCD 끔. 네이티브 2D이므로 **평면 제약 추가 비용이 없습니다**.
- 푸셔 `rapier3d-planar`(단층·평면 제약 비교 조건): 토큰 Y 이동과 X/Z 회전 잠금, 바닥 충돌 제외, 중력 0. 바닥 마찰이 없으므로 Custom과 같은 쿨롱 감속을 어댑터가 활성 바디에 적용합니다(이 루프 비용은 `어댑터` 시간으로 따로 측정).
- 푸셔 `rapier3d-stacked`(실제 3D 적층 후보): 중력·바닥 마찰·토큰 적층을 엔진이 처리. 판 위로 올라간 토큰은 고정 립이 후퇴 시 긁어 앞으로 떨어뜨립니다. 바닥 아래로 떨어져야 이탈이 확정됩니다(가장자리 쪽이면 보너스, 아니면 유실 → 재투입).
- 푸셔 판은 키네마틱 위치 기반 바디이며 위치는 공통 `pusherMotion`이 정합니다.

마찰·감쇠 계수는 엔진마다 의미가 다릅니다. Custom 플링코의 `friction`은 충돌 순간 법선 임펄스에 비례하는 접선 임펄스 상한(회전 없음)이고, Rapier `friction`은 회전 자유도를 포함한 접촉 쿨롱 계수(결합 규칙: 평균)입니다. 같은 0.08이어도 감각이 다릅니다. Custom 플링코에는 회전 동역학이 없어(회전은 표시용) 페그 위에 얹힌 원석이 굴러 떨어지지 않고 끼임 보정에 더 의존합니다. 적층 모드의 마찰은 법선력에 비례하는 엔진 접촉 마찰입니다. 각 측정 결과에 실제 설정값이 함께 기록됩니다.

## 화면 밖 처리와 숨김 탭

- **화면 밖 처리**를 켜면 물리 월드는 정지 상태로 보존됩니다(보드 위 원석·트레이 토큰·진행 중인 내부 이송의 남은 시간 그대로). 대기열에서 새로 꺼낸 원재료만 처리량(`plinkoReleasePerSec`)으로 즉시 완료 처리하며, 가공·부산물 점수는 화면 안에서 완료된 원재료의 평균(5개 미만이면 기본값)을 사용합니다. 부산물 낙하·압축·배출는 같은 규칙으로 진행하고, 투입구에 도착한 토큰은 **화면 밖 트레이 풀**에 쌓입니다. 풀은 화면 안에서 측정한 최근 30초 회수 가치/초(10초 미만이거나 0이면 기본값 12/s)만큼 앞에서부터 토큰을 지급합니다.
- 복귀 시 풀에 남은 토큰은 지급되지 않은 채 실제 투입구 앞쪽으로 돌아갑니다. 같은 시간을 두 번 처리하거나 지급한 토큰을 다시 지급하지 않습니다(테스트로 확인).
- **숨김 탭**은 타이머가 계속 돈다고 가정하지 않습니다. 숨김 중에는 프레임 루프가 아무것도 진행하지 않고, 복귀 시 숨김 시간을 측정해 같은 근사 모델로 최대 30분까지, 0.5초 청크(최대 3,600회)로 한 번에 정산하고 나머지는 버립니다. 브라우저 종료 후 오프라인 수익은 없습니다.
- 화면 밖 근사는 물리 성능 비교에서 제외됩니다(측정 중 전환하면 측정 취소).

한계: 근사는 평균값 모델이라 실제 궤적의 분산·적체(투입구 막힘)·물리 회수율 변화를 재현하지 않습니다. 화면 밖에서는 동시 수용량 제한도 적용하지 않습니다.

## 측정 방법

- 공통 시나리오(`src/lab/scenario.ts`): 시드, 장치 치수, 초기 원재료·적재 토큰 수와 배치(시드 섞음 육각 격자), 틱별 투입 일정, 공급·처리량, 푸셔 주기·스트로크, 고정 dt 1/60, 워밍업 20초·측정 10초·3회, 렌더 품질.
- `npm run measure:feel`: 푸셔 감각을 장시간(150초, 처음 45초 제외) 시드 3개로 측정합니다. 푸셔 왕복 1회당 낙하 수의 평균·변동계수·중앙값·p90·최대·0개 왕복 수(간헐적 붕괴 정도), 더미 최대·평균 층, 트레이 추이, 유실. `artifacts/feel.json`.
- 각 반복은 새 월드에서 시작합니다. 워밍업은 렌더 없이 빠르게 진행해 트레이가 정상 상태(푸셔 압력이 가장자리까지 전달)에 도달한 뒤 측정합니다. 측정 중 개수·품질을 자동으로 바꾸지 않습니다.
- 브라우저 측정은 시작 시 전체 입력 사본을 보관하고 매 반복에 복원합니다. 측정 중 자동 데모의 카메라 순회·추가 투입은 쉬며, 설정·개별 페그·수동 투입·배속·일시정지·초기화를 변경하면 측정을 취소합니다. 초기화 중 중복 측정 시작도 무시합니다.
- 결과 JSON의 `schemaVersion: 2`, `input`에는 공급·경제·장치·물리 계수·일정·개별 페그 설정을 포함한 전체 `Scenario`가 들어갑니다. `Simulation.create(cloneScenario(result.input))`으로 동일 입력을 복원할 수 있습니다. 기존 `scenario`는 표시용 요약으로 유지합니다. A/B 비교 경고는 백엔드 선택을 제외한 전체 입력 차이를 검사합니다. Node `--quick`도 실제 워밍업·측정 기간·반복 수를 입력에 기록합니다.
- 기록: 플링코·푸셔 step 중앙값·p95, 엔진 밖 어댑터 시간, 상태 전달(스냅숏) 비용, 프레임 CPU 시간·간격(브라우저), 활성·휴면 수, 초기화 시간, JS 힙 변화(Chrome만), 실제 원석·토큰 수, 겹침·튀어오름·유실·끼임 보정, 완료·회수 수, 버린 시간, 백엔드 설정. 지원하지 않는 값은 `측정 불가`로 표시합니다(Rapier 내부 WASM 메모리, 적층 형상의 겹침).
- 궤적·수익의 완전 일치는 요구하지 않습니다. 같은 엔진·같은 브라우저에서 입력은 재현되지만 엔진·브라우저 간 비트 단위 결정성은 보장하지 않습니다.
- 브라우저 측정은 개발 서버의 교차 출처 격리(COOP/COEP) 헤더로 `performance.now()` 해상도를 높입니다. 격리가 없으면 해상도가 0.1ms로 떨어져 basic 규모 step 값이 거칠어집니다.

### 권장 기본 구성

**플링코 Rapier 2D + 푸셔 Rapier 3D 적층**을 시나리오 기본값으로 두었습니다.

- 푸셔: 핵심 감각(여러 층 더미가 크게 무너짐)을 가장 잘 만드는 것은 Rapier 3D 적층이며, 토큰 약 700개까지 step 4.7–5.5ms(p95 7.3ms)로 60 Hz 예산 안입니다. 따라서 "기존 엔진이 목표 감각과 성능을 만족하면 채택" 기준을 **토큰 수백 개 규모에서** 충족합니다.
- 스트레스 목표(토큰 약 2,000개)는 Rapier가 21–30ms로 만족하지 못합니다. 이 규모가 필요하면 Custom 적층(약 1,730개에서 6ms)이 성능은 되지만, 현재는 큰 붕괴가 약해 감각 기준을 충족하지 못합니다. 두 방향 중 하나가 필요합니다: (a) 토큰 상한을 수백~1,000개로 두고 Rapier 사용(1,000개 규모 측정은 아직 안 함), (b) Custom 적층에 힘 누적·해제(stick-slip) 모델을 추가해 붕괴 규모를 Rapier에 맞춘 뒤 재측정.
- 플링코: 두 방식 모두 1ms 미만이며 Rapier 2D는 회전 덕분에 끼임 보정이 0회라 엔진을 채택합니다.
- Unreal 이식 시 엔진 측 후보는 Chaos이므로 같은 시나리오·감각 지표로 다시 측정해야 합니다.

## 알려진 한계

- 저장통은 `Silo2D`의 2D 원형 입자 물리입니다. 앞뒤 이동 없이 중력·서로 밀어내기·벽·경사 바닥·하단 게이트를 처리합니다. 다각형의 정확한 회전 충돌은 생략합니다. 표시 상한은 720개이며 실제로 들어가는 수량은 입자 크기와 저장통 내부 여유에 따라 더 작습니다. 빈자리가 생기면 상부 대기 재고에서 추가 유입됩니다. 넘치는 재고는 상부 유입 대기로 보존합니다.
- 내부 벨트·리프트는 외장 안의 시간 기반 경로이며 실제 강체 충돌을 계산하지 않습니다. 화면 밖 근사 후에는 남은 저장 수량에 맞춰 저장통 물리 입자를 동기화합니다.
- 부산물 더미는 `Silo2D`를 재사용하는 단일 평면의 원형 충돌 근사입니다. 납작한 파편의 정확한 다각형·3D 회전 충돌은 계산하지 않습니다. 쌓이는 동안 물리로 처리하고, 누르는 동안 `ScrapPress`가 안착한 조각과 받침을 동일 거리만큼 내리는 경로 기반 연출을 사용합니다. 조각을 변형하거나 재배열하지 않습니다. 압축 버퍼의 논리 수량과 별도로 물리 입자·유입 대기·압축부 도착 수량을 관리합니다. 숨김/화면 밖 근사 후에는 남은 재고를 명시적으로 재동기화하며 정상 생산에 이 경로를 사용하지 않습니다. 내부 처리와 출구 안의 수직 이송은 경로 기반이며 출구를 벗어난 코인은 강체 물리를 사용합니다.
- 정상 생산은 반드시 부산물 물리 더미 → 보이는 누름판·받침 하강 → 가림판 아래 도착 → 내부 처리·복귀 → 하부 이송 → 출구별 배출을 거칩니다. 초기 적재·비정상 유실 복구·화면 밖 근사 재고는 정상 생산 성공의 증거로 세지 않습니다.
- 프레스 한 사이클과 배출구 여유 때문에 과잉 공급 시 처리량이 제한됩니다. 아래의 기존 성능 측정은 측면 프레스·가로 이송 및 작업 폭 확대 이전 결과이며 이번 변경의 성능 개선을 주장하지 않습니다.

- Custom 적층 2.5D는 회전 동역학이 없습니다. 토큰이 세로로 서거나 굴러가지 않고, 기울기는 표시용이며 충돌은 항상 수평 원판입니다. 무너짐은 받침 밖 무게중심·경사·마찰 결합·하중 돌출의 경험 규칙이며 힘 누적이 없어 Rapier 같은 큰 일괄 붕괴(stick-slip)가 약합니다. 계수에 민감하고, 반복 수가 제한되어 깊은 더미에서는 압력 전달이 늦습니다.
- Custom 단층은 쌓임이 없어 참고용입니다.
- Custom 플링코는 원석 회전 동역학이 없습니다. 페그 정점 균형·원석끼리 받침에서 끼임 보정이 개입합니다.
- 페그와 벽 사이 틈이 원석 지름의 1.15배보다 좁은 가장자리 페그는 배치하지 않습니다(벽 끼임 방지).
- 렌더 보간이 없어 화면 주사율과 60 Hz 고정 스텝이 다르면 미세한 끊김이 있을 수 있습니다.
- 성능 수치는 측정 환경(아래 결과 표)에 한정됩니다. 다른 CPU·GPU·브라우저에서 다시 측정해야 합니다.

## Unreal 이식 메모

- 이식 대상은 `src/core`(GameCore·경제 공식·로컬 좌표 계약)를 C++로 재구현하고, 물리·렌더링 어댑터만 교체하는 구조입니다. TypeScript 코드는 동작 비교용 참조 구현이며, JS 런타임·웹뷰를 Unreal 실행 의존성으로 넣지 않습니다.
- `BoardFrame`은 Unreal `FTransform`(균일 스케일 검사 포함)에서 `u/v/n` 축을 뽑아 같은 공식으로 씁니다. Unreal 좌표계(왼손, Z 위)에서도 로컬 2D 계약과 이벤트 계약(사실만 보고, 지급은 코어)은 그대로입니다.
- 어댑터 계약: `init / spawn / remove / step(dt) / snapshot / drainEvents / stats / reset / dispose`. 엔진 콜백 정규화와 중복 방지는 코어가 아니라 어댑터·코어 경계에서 처리합니다.
